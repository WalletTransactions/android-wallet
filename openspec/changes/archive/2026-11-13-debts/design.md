# Design

## Context

Мотивация — proposal.md; продуктовые решения зафиксированы ответами в
issue `.github-private#10` и общие для четырёх парных changes. Серверная
сторона (таблицы, синк, функции) — change `debts` в wallet-api.

Что есть сейчас:

- Счёт — строка `account`; кошелёк — когда есть живая строка
  `account_operating` с тем же `_id` и `uuid`. Расширение кошелька таблицей с
  общим PK — `account_asset` (`capital-assets`): `WalletDbHelper`,
  `SyncEngine.TABLE_ORDER`, `applyAccountAsset`, `resolveAccountConflicts`,
  флаг перечита ledger в `AppSettings`.
- Операция — всегда проводка между двумя счетами; перевод «кошелёк → кошелёк»
  не доход и не расход (`GenerateIncomeReportByAccount` /
  `GenerateExpanseReportByAccount`, условия `acc_to_is_operating` /
  `acc_from_is_operating` по `v_operation_eq`). Отрицательный баланс кошелька
  — штатный случай.
- Все итоги остатков строятся из `WalletDbLoader.LoadBalancesPerWallet`
  (`WalletBalanceRow` с `assetType`, `includeInNetWorth`): карточка периода,
  таб «Кошельки», остатки в пикере.
- Выбор счёта при вводе операции — `AccountPickerActivity` (в режиме ввода
  скрывает системные категории); ввод — `TransactionActivity`.
- Системная категория, которая не расход, заводится лениво
  (`GetOrCreateSystemCategory`). Для долгов она не нужна (D8).
- Код живёт в `app/src/main/java/com/example/wallettransactions/`;
  тесты — JUnit + Robolectric; флейворы `prod`/`qa`.

## Goals / Non-Goals

**Goals:**
- Долг — обычные проводки и кошельки; всё, что работает с кошельками (синк,
  валюты, архив, отчёты), работает с займом без отдельной логики.
- Три действия при вводе вместо ручного выбора направления.
- Ликвидные итоги не искажаются; долги видны отдельно.
- Работа офлайн; конфликты имён контрагентов разрешаются как у счетов.

**Non-Goals:**
- Проценты, ставки, графики, напоминания (слой поверх тех же кошельков).
- Автоматическая привязка возвратов к займам: заём выбирает пользователь.
- Запрет «актив и долг» на сервере; клиент просто не предлагает.
- Подсказки «это долг?» в ИИ-карточке, импорте выписок и боте.

## Decisions

### D1. Таблицы `counterparty` и `account_debt`

По образцу `account_asset`:

- `counterparty`: `_id INTEGER PRIMARY KEY AUTOINCREMENT`, `name TEXT NOT
  NULL`, `comment TEXT NOT NULL DEFAULT ''`, `icon_uuid TEXT NULL`,
  `is_archived INT NOT NULL DEFAULT 0`, колонки синка (`SYNC_COLUMNS_DDL`),
  частичный уникальный индекс `uq_counterparty_name` по
  `AccountNames.keySql(name)` среди живых — тот же ключ, что у
  `uq_account_name` (регистр и «ё»/«е»), совпадает с серверным
  `lower(btrim(translate(name, 'Ёё', 'Ее')))` (wallet-api `000036`). Пробелы
  по краям обрезаются при вводе, до записи.
- `account_debt`: `_id INTEGER PRIMARY KEY` (= `account._id`, uuid = uuid
  счёта), `counterparty_uuid TEXT NOT NULL`, `comment TEXT NOT NULL DEFAULT
  ''`, `due_date TEXT NULL` (`yyyy-MM-dd`), колонки синка, FK на
  `account(_id)`.
- Снятие признака — мягкое удаление строки, повторная пометка — оживление
  той же строки (как у `account_asset`).
- Локальная `counterparty_contact(counterparty_uuid TEXT PRIMARY KEY,
  lookup_key TEXT NOT NULL)` — без колонок синка и без dirty-триггера.

*Альтернатива:* имя контрагента строкой в `account_debt`. Отклонено
владельцем (ответ на вопрос 9): отдельная таблица даёт архив, иконку и
одно место переименования.

### D2. Шаг БД и однократный перечит ledger

Версия — следующая свободная на момент реализации (сейчас в коде 90).
Шаг: создать три таблицы, `createDirtyTrigger` для двух синхронизируемых,
`createUuidIndex`, `CreateViews` (см. D5) и флаг «перечитать ledger» в
`AppSettings` — как у `capital-assets`. `onCreate` создаёт таблицы без
флага. Первый синк после обновления перечитывает ledger с нуля и один раз
помечает все живые `counterparty` и `account_debt` dirty (вторая линия
защиты от выката APK раньше сервера, см. Risks).

### D3. Синк

- `TABLE_ORDER`: `account_operating`, `account_asset`, `counterparty`,
  `account_debt`, `operation` — совпадает с `kApplyOrder` wallet-api.
- `collectDirtyByTable`: `counterparty` — `uuid, name, comment, icon_uuid,
  is_archived, deleted`; `account_debt` — `uuid, counterparty_uuid, comment,
  due_date, deleted` (ключи по `openapi.yaml` wallet-api, схемы
  `CounterpartyPushRow` / `AccountDebtPushRow`). `icon_uuid` и `due_date` на
  сервере необязательны и nullable, но клиент отправляет их всегда (`null` —
  «нет»): отсутствие ключа сервер трактует как «оставить прежнее», и снятие
  срока на телефоне иначе не доехало бы. `due_date` — строго `yyyy-MM-dd`,
  другое — `400 invalid_row`.
- `applyCounterparty`; `applyAccountDebt` ищет родительский счёт и
  контрагента по uuid, нет — пропуск с логом.
- `resolveAccountConflicts` расширяется: `409 duplicate_name` по
  `counterparty` (сервер отдаёт `existing_uuid`, как для `account`)
  переклеивает uuid строки на выжившую и обновляет
  `account_debt.counterparty_uuid`.
- `409 counterparty_in_use` на удаление контрагента — тело `{"error":
  "counterparty_in_use", "table": "counterparty", "uuid": …}`; по `uuid`
  вернуть строку (`deleted_at = NULL`), оставить dirty, показать в списке
  (design D12). Батч откатывается целиком, поэтому остальные строки
  остаются dirty и уходят следующим push.
- `409 missing_reference` для `account_debt` (кошелёк без
  `account_operating` или неизвестный контрагент) при соблюдении
  `TABLE_ORDER` и D12 не ожидается; если пришёл — обычная обработка
  `missing_reference`, без особого случая.
- `touchesAccounts` учитывает обе таблицы (перезагрузка кэша).

### D4. Модель и кэш

`Singleton`-кэш счетов получает `DebtInfo debt` на `AccountOperatingItem`
(`null` — не долговой): `counterpartyUuid`, `comment`, `dueDate`. Кэш
контрагентов — отдельный список в `Singleton`, инвалидируется вручную в
тех же местах, что и кэш счетов.

### D5. Признак «долговой» в SQL

Колонка `is_debt_wallet` (0/1) для каждой стороны в `v_operation` /
`v_operation_eq` (`LEFT JOIN account_debt … deleted_at IS NULL`),
пересоздаётся шагом БД. Её используют ровно три места: фильтр пикера и
подпись в ленте (D6) и «В долг / из долга» (D9). Доход и расход **не**
меняются — переводы и так в них не входят.

### D6. Действия при вводе и подпись в ленте

- В `AccountPickerActivity` в режиме выбора категории — три служебных
  пункта в начале списка (текстовые, не счета). Выбор запускает
  `DebtFlowActivity` (контрагент → заём → сумма/дата/комментарий), которая
  возвращает в `TransactionActivity` готовый перевод. «Вернуть» определяет
  направление по знаку баланса займа, при нулевом остатке не предлагается.
- Выбор займа: список кошельков контрагента в нужной валюте + «Новый заём».
  Валюта нового займа по умолчанию — валюта выбранного кошелька
  пользователя, можно сменить; разновалютная выдача идёт существующим
  путём перевода через `Transfer`.
- В обычных пикерах кошелька долговые кошельки скрыты при вводе новой
  операции (по `is_debt_wallet`); при правке существующей операции видны.
- Подпись: `OperationItem` получает вычисленное при загрузке ленты поле
  `debtLabel` (`GAVE`, `TOOK`, `REPAID`, `RETURNED`). Расчёт — один проход
  по проводкам займа в хронологическом порядке с накопленным остатком до
  проводки (правило из спеки). Правка задним числом пересчитывает при
  следующей загрузке; в базе подпись не хранится.

### D7. Контакты телефона — без разрешения

Выбор контакта — системный `Intent.ACTION_PICK` на
`ContactsContract.Contacts.CONTENT_URI`: система даёт временный доступ к
выбранному контакту, поэтому `READ_CONTACTS` не нужен и разрешение не
запрашивается. Из результата берём имя (`DISPLAY_NAME`) и `LOOKUP_KEY` →
`counterparty_contact`. Привязка нужна, чтобы открывать контакт из карточки
контрагента (`ACTION_VIEW` по lookup-uri); подсказок имён при вводе нет
(для них требовался бы `READ_CONTACTS`).

*Отличие от ответа владельца:* вопрос 5 звучал «связь с телефонной книгой —
нужна, а без доступа — текстом». Системный выбор даёт ту же связь без
разрешения; «без доступа — текстом» выполняется при отсутствии приложения
контактов или отмене выбора. Если нужны подсказки при наборе имени, добавим
`READ_CONTACTS` отдельно (запрос по тапу «Из контактов», отказ → текст).

### D8. Прощение — обычная категория

`ForgiveDebtDialog` создаёт проводку «долговой → категория» (расход) или
«категория → долговой» (доход) на выбранную дату (конец дня, как в
`archive-wallet-writeoff`); категория по умолчанию — обычная «Списание
долгов», создаётся при первом использовании как любая категория (не
системная, `system_kind = 0`): прощение — реальный расход или доход и должно
попадать в отчёты. Диалог повторяет структуру `ArchiveWriteOffDialog`.

### D9. Итоги и сверка периода

- `LoadBalancesPerWallet` отдаёт `debt` на `WalletBalanceRow` (тот же
  `LEFT JOIN`).
- `GenerateReportGetBalanceToDate` считает только строки без актива и без
  долга. Новый `GenerateDebtsToDate` из тех же строк даёт «Мне должны»
  (сумма положительных по кошелькам), «Я должен» (сумма модулей
  отрицательных), «Всего с долгами» и неполноту — с той же логикой
  `hasEq == false`.
- «В долг / из долга» = сумма проводок, где одна сторона — ликвидный
  кошелёк, а другая — долговой, за период, со знаком относительно
  ликвидного: выдача отрицательна, возврат положителен. Нужна, чтобы «На
  начало + Доход − Расход + В долг / из долга = На конец» сходилось
  (урок `summary-reconciliation`). Если есть и активы, их переводы
  учитываются так же в своей строке; пересечения «долг ↔ актив» не
  предусмотрены.
- Строки скрыты (`GONE`), пока нет ни одного долгового кошелька.

### D10. Экраны

- `DebtsActivity` («Долги»): `RecyclerView` с заголовками-контрагентами,
  вложенными займами, итогами сверху, переключателем «Закрытые». Данные —
  один запрос из `LoadBalancesPerWallet` + кэш контрагентов; группировка в
  коде.
- `DebtDetailActivity` (карточка займа): остаток, срок, комментарий,
  операции кошелька (существующий список с фильтром по кошельку), кнопки
  «Вернуть» и «Простить».
- `CounterpartiesActivity`: список, создание, переименование, архив,
  удаление; кнопка «Из контактов» (D7).
- Вход — из «Ещё» и из таба «Кошельки» (секция «Долги»).
- Тексты — строками ru/en (в проекте CI-проверка на захардкоженный текст).

### D11. Переплата

При сумме возврата больше текущего остатка займа — диалог-предупреждение
с подтверждением (текст в строках). Отказ оставляет форму без изменений.
Сам перевод — обычный, остаток становится отрицательным.

### D12. Конфликты и удаление контрагента

Контрагент удаляется локально только без живых `account_debt`. Если
удаление на другом устройстве конфликтует с новым долгом (`409
counterparty_in_use` при push), строка возвращается (D3); если контрагент
пришёл удалённым (tombstone) при pull, а у локального займа он остался,
займ не теряется — контрагент оживляется локально и отправляется заново.

### D13. ИИ-карточка и импорт выписок

Список кошельков, который собирают `ai-expense-entry` и
`ai-statement-import`, фильтруется по `debt == null` — как они уже не
предлагают системные категории. Остальное поведение не меняется.

### D14. Сброс данных

«Удалить все операции» операции долговых кошельков удаляет как любые;
долговые кошельки и контрагенты остаются с нулевым остатком (как обычные
кошельки). Контрагентов и займы сброс не трогает.

## Нужны ли правки в других сервисах

- **wallet-api:** да, парный change (`counterparty`, `account_debt`,
  порядок синка, `409 counterparty_in_use`, `kind = 'debt'`).
- **wallet-report:** да, парный change (`/debts`); телефон считает итоги сам
  из локальной базы, но веб и бот ходят в отчёты.
- **wallet-telegram:** да, парный change (убрать долговые кошельки).
- **wallet-ai, wallet-gateway, google-auth:** нет.

## Поведение без сети и при отказе сервера

Все действия работают офлайн: проводки, контрагенты и `account_debt`
пишутся локально и уходят при следующем синке. `409 duplicate_name` и
`409 counterparty_in_use` разрешаются при синке (D3, D12). Отказ push
(`5xx`/нет сети) оставляет строки dirty.

## Risks / Trade-offs

- [APK выходит раньше сервера] → push молча пропускает неизвестные таблицы,
  клиент снимает `dirty`, и данные не доедут. → Выкат строго: сервер раньше
  APK; вторая линия — однократная пометка dirty при первом синке (D2).
- [Пользователь вернул долг не на тот заём] → итог по контрагенту верен,
  остатки по займам расходятся; исправляется правкой операции.
- [Правка задним числом меняет подписи] → они вычисляются, не хранятся
  (D6).
- [Кошелёк и актив, и долг] → клиент не предлагает; схема не запрещает.
- [Контрагент в удалённом на другом устройстве состоянии, пока здесь есть
  долг] → D12.
- [Много кошельков в списке] → отдельная секция «Долги», закрытые скрыты.
- [Привязка к контакту живёт только на одном устройстве] → принято
  (ответ 5); на другом устройстве связь создаётся заново.

## Migration Plan

1. Дождаться wallet-api с таблицами на test (иначе push теряет данные).
2. Выкатить wallet-report и бота; затем APK.
3. После обновления первый синк перечитывает ledger и повторно отправляет
   `counterparty`/`account_debt`.
4. Откат: предыдущей версией приложения; таблицы остаются в базе
   неиспользуемыми, долговые кошельки становятся обычными.

## Open Questions

  `READ_CONTACTS`)? Сейчас — нет, только системный выбор контакта (D7).
