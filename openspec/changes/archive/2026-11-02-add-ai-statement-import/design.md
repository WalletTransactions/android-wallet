# Design

## Context

Импорт выписки делает wallet-ai: change `add-statement-import` (44 из 50
задач), контракт — `wallet-ai/openapi.yaml`, `/api/ai/imports*`. Сервер ничего
не пишет в кошелёк: отдаёт строки, группы и готовые операции, клиент пишет сам и
отмечает записанное. Веб-клиент (`wallet-web`, change `add-ai-statement-import`)
ещё не начат, поэтому Android будет первым клиентом импорта.

**Разделение ролей (решение 2026-10-24).** Задача ИИ — разобрать выписку и
предложить категории. Проверку на дубли клиент делает сам, по полям операций в
своей базе. Серверные механизмы дублей — `op_uuid`/отпечаток,
`statement_imported`, группы `exists`, `imported`, `possible_duplicate` — Android
не использует и на них не опирается.

Что важно из сервера:

- У каждой строки есть `row_id` (uuid v4, `statement_row.id`): стабилен, пока
  жив импорт; новая загрузка той же выписки — новые `row_id`.
- `op_uuid` (uuid v5 от отпечатка строки) зависит от `pattern`, а тот — от
  `description`, которую пишет модель (`verify.cpp`). После смены промпта у
  той же строки может быть другой `op_uuid`. Для клиента это ещё одна причина
  не строить на нём защиту от дублей.
- `PATCH /rows`: смена категории учит правило продавца и проставляет
  категорию похожим строкам. Смена суммы или даты меняет серверный отпечаток.
- `POST /committed {row_ids}` замораживает строки; когда записаны или
  отклонены все, импорт `done`.
- Группы строк: `ready`, `needs_category`, `possible_duplicate`, `check`,
  `exists`, `imported`, `income_transfer`. Change wallet-ai
  `add-statement-transfers` (не начат) делит `income_transfer` на `income` и
  `transfer` и добавляет `ignored` — **BREAKING** для клиента.

Телефон:

- Окно операции `TransactionActivity` принимает префилл через extras (`cDate`,
  `cAmount`, `cFrom`, `cTo`, `cComment`, `cKind`), но uuid генерирует само: на
  расходе — прямой `db.insert` со случайным uuid, на переводе и комиссии —
  `WalletDbCRUD.InsertOperation`.
- В локальной SQLite **нет уникальности `operation.uuid`**. На сервере
  `operation` — `PRIMARY KEY (ledger_id, uuid)`, push с тем же uuid обновляет
  строку. Две локальные операции с одним uuid после синка дают расхождение:
  на телефоне две траты, на сервере одна.
- В базе телефона после синка лежат все операции кошелька, включая записанные
  в вебе и боте. По ним можно искать дубли без сети.
- Из `add-ai-client` переиспользуются: синк перед запросом
  (`SyncRunner.runOnceShared`), сверка серверных uuid с локальной базой
  (`DraftReconciler`), клиент `AiApiClient`.

## Goals / Non-Goals

**Goals:**
- проверка выписки на телефоне: список строк, правка в привычном окне
  операции, запись по одной и пачкой;
- ни одной операции дважды по ошибке: ни повторным «Сохранить», ни повторной
  загрузкой той же выписки — проверкой на телефоне, а не на сервере;
- сервер знает, что записано (отметка строк, обучение правил категорий).

**Non-Goals:**
- своя копия строк импорта на телефоне и работа со списком без сети;
- серверная защита от дублей в роли источника правды для клиента;
- правка суммы и даты через сервер (`PATCH`) — только локально;
- конструктор формата выписки и правила импорта — в вебе.

## Decisions

### 1. Источник: файл из «Поделиться» или выбор файла

Выписку на телефоне обычно отдаёт банковское приложение через «Поделиться»
(PDF/CSV). Экран импорта принимает `ACTION_SEND` с `EXTRA_STREAM`
(`application/pdf`, `text/csv`, `text/comma-separated-values`, `text/plain`) и
открывается выбором файла (`ACTION_OPEN_DOCUMENT`). Файл до 5 МБ уходит
base64 в `POST /api/ai/imports` (D9 wallet-ai: JSON, не multipart).

Кошелёк выписки пользователь выбирает перед загрузкой: только живые
неархивные, серверу нужен `wallet_uuid`. Перед `POST` выполняется синк
(`runOnceShared`), как в `add-ai-client`: кошелёк, созданный на телефоне, иначе
серверу неизвестен (`400 unknown_wallet`). Этот же синк приносит операции из
веба и бота — по ним решение 7 ищет дубли.

### 2. Список строк — всегда с сервера

Строки импорта на телефоне не хранятся: экран каждый раз берёт
`GET /api/ai/imports/{id}`. Незавершённый импорт после перезапуска находится
через `GET /api/ai/imports`. Без сети список не открывается, экран так и
говорит. Вторую копию, которую надо сверять с сервером, не заводим.

### 3. uuid операции = `row_id` строки; «добавлено» — живая операция с ним

Операция из строки импорта сохраняется с `uuid = row_id`. Отдельного флага
нет: строка добавлена, если в базе телефона есть `operation` с этим uuid и
`deleted_at IS NULL` (с учётом uuid без дефисов — `LocalUuid.find`). Это
переживает перезапуск приложения. Если пользователь потом удалит операцию,
строка снова станет «ждёт». Добавленная локально, но не отмеченная на сервере
строка (`committed: false`, например не было сети) при следующем открытии
списка дошлётся в `POST /committed`.

Почему `row_id`, а не серверный `op_uuid`:
- `row_id` есть у каждой строки уже сейчас — правка wallet-ai не нужна
  (`op_uuid` отдаётся только у группы `ready`);
- `row_id` не зависит от промпта, суммы и даты: правка на телефоне его не
  трогает;
- узнавать повторную загрузку выписки по uuid клиенту не нужно — это делает
  решение 7 по полям.

Следствие для сервера: его сверка не узнает записанную операцию по
`op_uuid`, и строки других импортов могут получать `exists` или
`possible_duplicate` иначе, чем с `op_uuid`. Клиент эти группы не использует
(решение 8), так что на поведение телефона это не влияет.

### 4. Правка — в стандартном окне операции

Тап по строке открывает `TransactionActivity` с префиллом: кошелёк импорта,
категория строки (или пусто), сумма, дата, комментарий. Новый extra — uuid, с
которым сохранять. Окно умеет то, чего нет в списке: клавиатура суммы,
перевод, валюта, комиссия, валидация.

Правки окна:
- extra `cOpUuid`. Расход сохраняется с ним вместо случайного, на переводе его
  получает основная проводка (вторая нога и комиссия — свои случайные);
- если живая операция с этим uuid уже есть, окно открывает её **на
  редактирование**, а не создаёт новую (решение 6);
- подсказка модели (`suggestion`) идёт первой в пикере категорий.

Порядок после «Сохранить» (возврат в список):
1. операция в базе телефона с `uuid = row_id`;
2. если категория отличается от серверной — `PATCH /rows {category_uuid}`:
   сервер выучит правило продавца и подставит категорию похожим строкам;
3. `POST /committed {row_ids}`;
4. фоновый синк (`runOnce` без ожидания).

Сумму и дату через `PATCH` не отправляем: исправленные значения живут в
операции на телефоне, а строке на сервере хватает того, что она записана.

Шаги 2–3 без сети не проходят. Тогда операция уже записана локально, а строка
отметится при следующем открытии списка (решение 3).

### 5. «Записать готовые»

Кнопка пишет строки, у которых есть всё для записи: категория выбрана, кошелёк
и категория живы на телефоне (`DraftReconciler`), сумма и дата проходят
проверки, решение 7 не нашло похожую операцию. Пишутся одной транзакцией
SQLite с `uuid = row_id`, затем `POST /committed` по их `row_id` и фоновый синк.
Пропущенные строки остаются в списке с причиной. Их записывают по одной через
окно операции.

Основа — поля строк `rows[]`, а не `operations[]` сервера: состав «готовых»
определяет клиент, с учётом своей проверки дублей.

### 6. Один uuid — одна операция на телефоне

Перед любой вставкой из импорта — проверка, есть ли операция с этим uuid.
Есть живая — не вставляем: окно открывает её на правку, «Записать готовые»
пропускает. Есть удалённая (`deleted_at`) — восстанавливаем ту же строку с
новыми полями, а не создаём вторую с тем же uuid.

Вторая линия — **уникальный индекс `operation(uuid)`** миграцией локальной
базы. На копии базы с телефона (24.10.2026, 8595 операций) дублей и пустых
uuid нет. Миграция всё равно сначала сводит возможные дубли (оставляет одну
строку на uuid, остальные помечает удалёнными), иначе на чужой установке
`CREATE UNIQUE INDEX` упадёт.

### 7. Дубли — проверка на телефоне по полям

Для каждой ещё не добавленной строки телефон ищет в своей базе живую операцию:
- тот же кошелёк (кошелёк импорта — источник для расхода, получатель для
  дохода);
- та же сумма (точно, в валюте кошелька);
- дата в пределах ±1 дня (банк проводит покупку на следующий день);
- операция не из этого импорта (`uuid` не равен `row_id` ни одной строки).

Сопоставление один к одному: каждая операция кошелька закрывает не больше
одной строки. Строки идут по дате, кандидат — ближайший по дате. Так два
одинаковых кофе за день в выписке при одном записанном кофе дают одну
«похоже» и одну «ждёт».

Строка с кандидатом показывается как «Похоже, уже есть: 12.10 450,00 Такси».
В «Записать готовые» она не попадает. «Записать всё равно» — только по одной
через окно операции. Поиск идёт по локальной базе, поэтому работает и без
сети, если список уже открыт.

Повторная загрузка той же выписки ловится этим же правилом: её строки получат
новые `row_id`, но найдут записанные в прошлый раз операции по полям.

Для свободной формы (`add-ai-client`) ничего не меняется: там uuid случайный,
каждая запись — новая операция, дубли разрешены (человек мог купить два кофе).

### 8. Группы сервера — подсказка, а не правило

Из групп сервера клиент берёт только то, что относится к разбору:
- `needs_category` — нет категории, строка ждёт выбора;
- `check` — сумма, дата или валюта не сверились с текстом (`check`), строку
  надо открыть и проверить;
- `income_transfer` (и будущие `income`, `transfer`, `ignored`) — не расход,
  MVP её не пишет.

Дублевые группы `exists`, `imported`, `possible_duplicate` клиент считает
обычными строками и проверяет их своим правилом (решение 7). Незнакомая
группа показывается как «не для записи» с исходной строкой выписки, без
кнопок записи. Так выход `add-statement-transfers` не ломает приложение.

### 9. Ожидание разбора — только на открытом экране

Решение 2026-10-24. Экран импорта опрашивает `GET /api/ai/imports/{id}`, пока
он открыт, и показывает `progress` и паузу (`paused_since` — LLM недоступна).
Ушли с экрана — опрос прекращается, разбор на сервере идёт дальше. Вернулись
(или открыли заново после перезапуска) — экран находит импорт через
`GET /api/ai/imports` и продолжает. Фонового опроса через WorkManager и
уведомления «Выписка разобрана» нет.

### 10. Только расходы

Решение 2026-10-24. Записываются только строки-расходы: кошелёк импорта →
категория. Доходы, переводы и всё из `income_transfer` (после
`add-statement-transfers` — `income`, `transfer`, `ignored`) показываются как
«не для записи» (решение 8). Change не ждёт `add-statement-transfers`. Доходы
и переводы — отдельным change, когда сервер их отдаст.

### Правки в других сервисах

Нет. wallet-ai используется по текущему контракту: `row_id`, поля строк,
`PATCH /rows` (только `category_uuid`), `POST /committed`. `/api/ai/*` и
`ai:use` уже есть (`add-ai-client`). wallet-api, google-auth, wallet-gateway — без
изменений.

## Risks / Trade-offs

- [Без сети список не открыть] → осознанно (решение 2). Записанное раньше
  остаётся в базе телефона, недошедшие отметки досылаются потом.
- [Разбор длится минуты (LLM на GTX 1070, фрагменты по ~1800 символов)] →
  экран показывает `progress`, с него можно уйти и вернуться; импорт
  находится через `GET /api/ai/imports`.
- [Ложное «похоже»: две разные покупки на одну сумму в один день, одна уже
  записана вручную] → строка не теряется, а ждёт решения; «Записать всё
  равно» в окне операции.
- [Пропуск дубля: сумму записанной вручную операции округлили или указали в
  другой валюте] → правило точное по сумме, такие строки уйдут в «готовые».
  Расширять допуск — после реальных выписок; список перед «Записать готовые»
  показывает, что именно будет записано.
- [Операции из веба или бота не дошли до телефона] → синк перед загрузкой
  (решение 1); при открытии списка — тоже синк, затем проверка.
- [Строка отмечена `committed`, а пользователь потом удалил операцию на
  телефоне] → строка на сервере заморожена, из этого импорта её не записать
  повторно; записать заново можно вручную.
- [Переделка групп в wallet-ai (`add-statement-transfers`)] → решения 8 и 10:
  пишем только расходы, незнакомые группы не ломают экран.
- [Разбор закончился, пока экран закрыт, — пользователь не узнает сам] →
  осознанно (решение 9): вернулся на экран — увидел готовый список.
