# Design

## Context

Мотивация и решения по вариантам — proposal.md и разбор в issue
https://github.com/WalletTransactions/.github-private/issues/1. Здесь — как это
ложится на код телефона.

Что есть сейчас:

- Счёт — строка `account`; кошелёк — когда есть живая строка
  `account_operating` с тем же `_id` и тем же `uuid` (общий первичный ключ,
  `WalletDbHelper.CreateAccountOperatingEntry`, `InsertAccountOperatingEntry`).
  `account.kind` проставляется один раз и не меняется (`AccountItem.Kind`).
- Системные категории — `account.system_kind` (`AccountItem.SystemKind`:
  `TRANSFER(1)`, `TRANSFER_COMMISSION(2)`), незнакомое значение читается как
  `NONE`. CHECK на `system_kind` в схеме телефона нет. Заводятся лениво через
  `WalletDbCRUD.GetOrCreateSystemCategory`, ищутся по `system_kind`.
- Доход — проводки `категория → кошелёк`, расход — `кошелёк → категория`
  (`WalletDbLoader.GenerateIncomeReportByAccount` /
  `GenerateExpanseReportByAccount`, условия `acc_to_is_operating` /
  `acc_from_is_operating` по `v_operation_eq`; те же условия у плиток
  `DataFilter.OperationKind.income/expense`). Перевод кошелёк → кошелёк ни
  туда, ни туда не попадает — покупка актива переводом уже сейчас уходит из
  расходов без правок.
- Балансы и итог — одна реализация `WalletDbLoader.LoadBalancesPerWallet`:
  из неё строятся карточка периода (`GenerateReportGetBalanceToDate` →
  `BaseTabActivity.refreshSummaryCard`), таб «Кошельки»
  (`AccountActivity.buildWalletRows`) и остатки в пикере
  (`AccountPickerActivity.buildRows`).
- Синк: `SyncEngine.TABLE_ORDER`, сбор `collectDirtyByTable`, применение
  `applyRow`/`applyAccountOperating`; незнакомые таблицы pull молча
  пропускает (цикл по `TABLE_ORDER` в `applyPage`), а курсор ledger при этом
  уходит вперёд (`AppSettings.setLedgerSyncSeq`). Сервер так же молча
  пропускает незнакомые таблицы в push (`wallet-api/src/sync_repo.cpp`).
- Конфликт имени счёта (409 `duplicate_name`) клиент решает переклейкой uuid
  на выжившую строку — `SyncEngine.resolveAccountConflicts`, вместе с
  `account_operating.uuid`.
- Аналога серверной `f_wallet_turnover_for_period` на телефоне нет: «оборота
  кошелька» как отчёта здесь не существует (см. Open Questions).

## Goals / Non-Goals

**Goals:**
- Признак актива — отдельная синхронизируемая таблица, старые версии
  приложения не ломаются (видят актив обычным кошельком).
- Одно место, где решается «это переоценка», — его используют все
  доходно-расходные запросы и фильтр.
- Все итоги по-прежнему строятся из одного запроса балансов, только
  разбиваются по признаку актива.

**Non-Goals:**
- Механизм минимальной версии клиента и защита от выкатки клиента раньше
  сервера в коде (только порядок выкатки).
- Абсолютная оценка отдельно от проводок, пересчёт Δ при правке прошлого.
- Подсказки «в актив?» в ИИ-карточке, импорте выписок и боте.

## Decisions

### 1. Таблица `account_asset` — по образцу `account_operating`

`_id INTEGER PRIMARY KEY` (= `account._id`), `asset_type INT NOT NULL`
(1 — недвижимость, 2 — авто, 3 — прочее), `include_in_net_worth INT NOT NULL
DEFAULT 1`, `comment TEXT NOT NULL DEFAULT ''`, колонки синка
(`SYNC_COLUMNS_DDL`), FK на `account(_id)`. `uuid` всегда равен
`account.uuid` того же счёта — как у `account_operating` и как в серверной
таблице (wallet-api, парный change).

- Снятие признака — мягкое удаление строки (`deleted_at`), повторная пометка
  — оживление той же строки (`deleted_at = NULL`): второй строки с тем же uuid
  быть не может.
- Признак допустим только у счёта с живой `account_operating`; UI предлагает
  его только кошелькам. Проверку на сервере делает wallet-api.
- Альтернативы (`account.kind = 2`, колонка в `account_operating`) отклонены
  в разборе: первая ломает смысл у старых клиентов, вторая — их push.

### 2. Шаг БД и однократный перечит ledger

Версия — следующая свободная на момент реализации (сейчас в коде 84; 84/85
заявлены `server-managed-icons` и `currency-ui-tweaks`, номер согласовать при
слиянии). Шаг: `CREATE TABLE account_asset`, `createDirtyTrigger`,
`createUuidIndex`, `CreateViews` (см. п. 5), и флаг в `AppSettings`
«перечитать ledger». `onCreate` создаёт таблицу без флага (курсор и так 0).

`SyncEngine.pullAll` при поднятом флаге ставит курсор ledger в 0 (reference и
`ledger_id` не трогает) и сразу снимает флаг. Дальше работает обычное
постраничное сохранение курсора — обрыв продолжает с последней страницы, а
upsert по uuid делает перечит идемпотентным. Тот же путь уже используется при
смене леджера (`pullAll`, сброс при чужом `ledger_id`).

Альтернатива — не перечитывать: при допущении «все устройства обновлены до
выкатки» пропущенных строк нет, но любое забытое устройство молча теряло бы
признаки активов навсегда. Цена перечита — один длинный pull (десятки тысяч
операций, индексы uuid есть с v82).

### 3. Синк `account_asset`

- `TABLE_ORDER`: после `account_operating`.
- `collectDirtyByTable`: `uuid, asset_type, include_in_net_worth, comment,
  deleted` — ключи по контракту wallet-api (`openapi.yaml`, `/sync/push`).
- `applyAccountAsset` — копия логики `applyAccountOperating`: родительский
  счёт ищется по тому же uuid; нет счёта — строка пропускается с логом.
- `resolveAccountConflicts` переклеивает и `account_asset.uuid`, иначе
  после 409 актив отправлялся бы со «старым» uuid несуществующего счёта.
- `touchesAccounts` учитывает `account_asset` (перезагрузка кэша счетов).

### 4. «Переоценка» — `SystemKind.REVALUATION(3)`

- Новое значение enum, `fromValue(3)`; `AccountItem.isSystemRevaluation()`.
- Заводится лениво `GetOrCreateSystemCategory(db, 3, "Переоценка", …)`.
  Если обычная категория с именем «Переоценка» уже есть (уникальность имени,
  v80), берётся имя «Переоценка активов». Чужую категорию в системную не
  превращаем: её прошлые проводки внезапно ушли бы из расходов.
- Две офлайн-копии на разных устройствах с одним именем сольются штатно через
  409 `duplicate_name`. С разными именами получатся две системные категории —
  безвредно, потому что исключение идёт по `system_kind`, а не по id.
- Защита от удаления/переименования уже общая (`isSystem()`,
  `DeleteAccount`); в `AccountItemActivity` — третья подсказка (текст в спеке).

### 5. Где решается «это переоценка»

Колонка `is_revaluation` в `v_operation` / `v_operation_eq` (1, если у одной
из сторон `system_kind = 3`), вьюхи пересоздаются шагом БД. Её используют:
`GenerateIncomeReportByAccount`, `GenerateExpanseReportByAccount`,
`DataFilter.OperationKind.income/expense` (`AND is_revaluation = 0`),
`CountOperations`/`LoadWalletIdsWithOperations` через тот же фильтр.

Альтернатива — `NOT EXISTS (… system_kind = 3)` в каждом запросе: четыре
копии одного условия, забытая — молча разъехавшиеся цифры (главный минус
варианта A из разбора).

### 6. Модель и балансы

- `AccountOperatingItem` получает `AssetInfo asset` (`null` — ликвидный):
  тип и `includeInNetWorth`; `LoadAccounts` — `LEFT JOIN account_asset … AND
  deleted_at IS NULL`.
- `LoadBalancesPerWallet` возвращает `assetType` (null — ликвидный) и
  `includeInNetWorth` на `WalletBalanceRow` (тот же `LEFT JOIN`). Запрос
  остаётся единственным.
- `GenerateReportGetBalanceToDate` считает только ликвидные строки — смысл
  «итога» меняется, вызовы нет. Новый `GenerateCapitalToDate` из тех же
  строк даёт два `EquivalentResult`: капитал и «всего с капиталом», с той же
  логикой неполноты (`hasEq == false` → не складывается, `incomplete`).

### 7. Экраны

- `view_period_summary.xml`: под балансами две строки (по умолчанию `GONE`) —
  «Капитал» и «Всего с капиталом» на конец периода (п. 11); `refreshSummaryCard`
  показывает их, если есть хотя бы один актив.
- `AccountActivity`: `WalletBalanceAdapter` получает строки-заголовки секций
  («Ликвидные», «Капитал» с суммой); без активов заголовков нет. Сортировка
  «самый толстый первым» — внутри секции. Колонка изменения за период у
  актива включает переоценку — это и есть изменение его стоимости.
- `AccountPickerActivity`: в режиме ввода — стабильное разбиение «ликвидные,
  затем активы» поверх выбранной сортировки, категория с `system_kind = 3`
  скрыта; в режиме справочника — всё как раньше плюс подпись типа актива.
- `AddWalletActivity` / `AccountItemActivity`: переключатели и выбор типа;
  запись — `WalletDbCRUD.SetAccountAsset(db, accountId, type, include)` /
  `ClearAccountAsset` в одной транзакции с остальным сохранением.
- `TransactionArrayAdapter`: третий тип строки `TYPE_REVALUATION` (новый
  layout на основе строки перевода), `getViewTypeCount() = 3`;
  `GroupedItems.addGroupedItem` не добавляет переоценку в итог дня.
  `OperationItem.isRevaluation()` — по `systemKind` сторон.

### 8. Диалог переоценки

`RevaluationDialog` (по образцу `RateEditDialog`) из `AccountItemActivity`.
Баланс на дату — новый `WalletDbLoader.LoadAccountBalanceAt(db, accountId,
endOfDay)`: все живые проводки актива с датой не позже конца выбранного дня.
Операция пишется на конец выбранного дня (23:59:59), чтобы стоять после всех
операций того дня и Δ совпадала с тем, что показал диалог. Комментарий —
«Оценка: <новая оценка>», чтобы абсолютное значение было видно в ленте и в
правке. Δ округляется до `precision` валюты актива. После записи —
`PeriodFilterState.markDataChanged()` и синк в фоне, как «Записать» на
экране «ИИ» (`new Thread(() -> SyncRunner.runOnce(app))`).

### 9. Перенос операций категории в актив

`WalletDbCRUD.MoveCategoryToAsset(db, categoryId, assetId)` в одной
транзакции, результат — `{moved, skippedNoRate}`:

- живые операции, где одна сторона — категория, другая — кошелёк;
- валюта кошелька = валюте актива: заменить сторону-категорию на актив;
- иначе — курс `LoadRateOnDate(валюта кошелька → валюта актива, дата)`:
  нет курса — пропустить и посчитать; есть — та же форма, что
  `TransactionActivity.saveTransfer`: исходная проводка становится
  `кошелёк → Transfer`, новая нога `Transfer → актив` на сумму × курс
  (округление до `precision` актива), `LinkOperations(…, LEG)`. Для
  возврата (`категория → кошелёк`) — зеркально: `актив → Transfer` и
  `Transfer → кошелёк`, исходная сумма остаётся на стороне кошелька;
- правила повторяющихся операций (`recurring_operation`, только локальные) с
  этой категорией и кошельком в валюте актива перенацеливаются на актив;
  разновалютные правила остаются как есть (см. Risks);
- категория без оставшихся живых операций помечается архивной.

После — перезагрузка кэша счетов (`Singleton`), `markDataChanged()`, синк в
фоне. Делает это клиент, не сервер: офлайн-устройство с неотправленными
операциями на старую категорию после серверной миграции привезло бы их
обратно (разбор, §5).

### 10. Пересчёт табов после изменения признака (android-wallet#42)

Табы (`BaseTabActivity`) перечитывают карточку периода и список только при
смене ревизии `PeriodFilterState` (`onResume` / слушатель `markDataChanged`).
Найдено при проверке #33: «Операции» показывали старые итоги после пометки
кошелька капиталом, пока не сменить дату.

Причины:
- `AccountItemActivity.save` поднимал ревизию только после списания остатка
  (archive-wallet-writeoff), `AddWalletActivity` — никогда. «Операции» — это
  другая Activity в стеке, её `onActivityResult` не вызывается.
- `SyncEngine.applyAccountAsset` не писал в журнал синка; `SyncRunner` поднимает
  ревизию только при непустом журнале — pull, принёсший одну строку
  `account_asset`, экраны не обновлял.

Решения:
- Ревизию поднимают оба экрана после любой успешной записи, а не только при
  изменении признака: имя, иконка, архив и валюта кошелька тоже видны на табах
  (лента, карточка, «Кошельки»), а лишний пересчёт при возврате на таб дешевле
  ещё одного незамеченного случая.
- У `account_asset` — свой тип в журнале синка, «Признак актива» / «Asset flag»,
  и в pull, и в push. В отличие от `account_operating` он не всегда идёт вместе
  со строкой `account`: пометка меняет только `account_asset`, и без строки
  журнала изменение было бы невидимо и для диалога синка, и для ревизии.
- Переоценка (`RevaluationDialog`) ревизию уже поднимала — только тест.

### 11. Две строки капитала в карточке периода (android-wallet#43)

Владелец при проверке #33 попросил разделить строку «Капитал · Всего с
капиталом» надвое. Спека и так говорила о двух строках, но в вёрстке две
подписи и две суммы шли в одной горизонтальной строке. Сумма «Всего с
капиталом» не стояла в колонке сумм под «На конец», а на узком экране подписи
слипались с суммами.

Решения:
- Две `LinearLayout` по образцу «На начало»: подпись `0dp`/`weight=1`, сумма
  `wrap_content` у правого края. Цвета и размеры прежние: «Капитал» — вторичный
  цвет, «Всего с капиталом» — основной (это итог).
- Id `capitalRow` остаётся за строкой «Капитал», новая — `netWorthRow`; id
  сумм не меняются. Видимость у двух строк общая (одна переменная в
  `refreshCapitalRow`), расчёт (`GenerateCapitalToDate`) тот же.
- Отдельной вёрстки для планшета нет (у карточки нет `layout-w*`): строки
  растягиваются по ширине карточки так же, как «На начало».

### Правки в других сервисах

- **wallet-api** (парный change): таблица `account_asset` в push/pull и
  `kApplyOrder`, `system_kind IN (0,1,2,3)`, исключение переоценки в
  SQL-функциях отчётов, признак актива в балансах. Без неё телефон теряет
  признаки (см. Risks).
- **wallet-report**, **wallet-web**: свои парные changes, телефона не
  касаются.
- **google-auth, wallet-ai, wallet-gateway**: правок нет.

### Без сети и при отказе сервера

Всё (пометка актива, переоценка, перенос категории) пишется в локальную базу
и видно сразу; строки остаются `dirty` до успешного push. Отказ сервера —
исход синка «ошибка»/«нет сети», данные ждут следующего прохода. 409 по имени
«Переоценки» или актива решается переклейкой uuid (п. 3, 4).

## Risks / Trade-offs

- [Клиент выкачен раньше сервера: push `account_asset` сервер молча
  пропускает, клиент снимает `dirty` — признак пропадает без ошибки] →
  строгий порядок выкатки (сервер, затем APK) и проверка в tasks: актив,
  помеченный на одном устройстве, виден на другом после синка.
- [Старая версия приложения: актив в её итоге, переоценка — в её доходе и
  расходе] → допущение «все устройства обновляются до выкатки» (ответ 5 в
  issue); балансы при этом верные.
- [Δ хранится проводкой: правка прошлых операций актива сдвигает
  последующие оценки] → принято вариантом A; абсолютная оценка видна в
  комментарии проводки, переоценку можно ввести заново.
- [Итог «ликвидные»: покупка актива выглядит падением «Итога» карточки без
  расхода] → строки «Капитал» и «Всего с капиталом» рядом объясняют
  движение; это прямое следствие ответа 2.
- [Однократный перечит ledger — долгий первый синк после обновления] →
  постраничный курсор переживает обрыв; повторно не выполняется.
- [Разновалютное правило повторяющейся операции на перенесённую категорию
  продолжит заводить расход на архивную категорию] → редкий случай; правило
  видно в «Повторяющихся операциях», пользователь правит его вручную.

## Migration Plan

1. Выкатить wallet-api (миграция + синк `account_asset`) и wallet-report.
2. Проверить на test: push/pull `account_asset` между двумя устройствами.
3. Раздать APK на все устройства (допущение ответа 5), затем пользоваться
   активами.
4. Откат клиента: старый APK не знает `account_asset` — признаки остаются
   на сервере и в базе (таблица не удаляется, понижение версии БД Android
   не поддерживает без переустановки), отчёты старой версии считают
   переоценку доходом/расходом.

## Open Questions

- Оборот кошелька: контракт требует исключить переоценку из Android-аналога
  `f_wallet_turnover_for_period`, но такого отчёта на телефоне нет — правка
  не нужна, пока он не появится.
- Перенос категории: операция категории, уже связанная `operation_link`
  (на практике у обычных категорий не встречается), при разной валюте
  пропускается; нужно ли отдельное сообщение — решить при реализации.
- Иконка «Переоценки»: подобрать из каталога при реализации (запасная —
  `unknown`, как у `createCategory`).
