# Design

## D1. Поле в счёте, а не отдельный раздел
`icon_image` лежит прямо в элементе `accounts`: картинка едет вместе с тем, чему
принадлежит, порядок разделов не меняется, файл без поля читается как раньше.
Цена — одна и та же картинка повторяется у счетов с общей иконкой; для личных
иконок это редкость, а отдельный раздел `icons` потребовал бы ещё и ссылок по
имени с проверками.

## D2. Имя иконки
`icon`, если задан и не `unknown`; иначе имя счёта. `unknown` — общая заглушка,
перезаписывать её картинкой нельзя.

## D3. Размер и формат
256×256, WEBP q85 — как `IconEditDialog` (`ICON_SIZE_PX`, `ICON_FORMAT`): самое
крупное место показа — ячейка 48dp (192px на xxxhdpi) и `getBitmap64()` (164px).
Не квадрат — обрезка по центру (как круглая обрезка редактора), потом масштаб.
Файл любого размера допустим; потолок — 1,5 млн символов base64, чтобы файл с
фотографией не раздувал базу и память.

## D4. Битая картинка не роняет счёт
Решение владельца: картинка — украшение, потеря которого не должна отбрасывать
счёт и его операции (операции ссылаются на счёт по имени). `decodeIconImage`
возвращает `null` на любой сбой; дальше иконка выбирается прежним путём
`LiveIconIdOrUnknown` (по имени, иначе `unknown`). Ошибка в отчёт не попадает —
как и для неизвестного имени иконки сегодня.

## D5. Существующая иконка
Своя (`origin=local`) — обновляется картинкой из файла (повторный импорт чинит
картинку). Серверная (`origin=server`) — не трогается: её правит администратор на
сайте, и она приходит синком; счёт на неё просто ссылается.

## D6. Экспорт
`icon_image` — base64 хранимого BLOB только у `origin=local`. Серверные иконки
восстанавливаются по имени, `unknown` — не картинка пользователя.
