# Design

## Context

Фильтр один на процесс: `PeriodFilterState` держит id счетов, тип операции, текст
и границы сумм и дублирует их в `AppSettings`. Из него собирается `DataFilter`,
который уходит в `WalletDbLoader`. Мотивация и состав — в `proposal.md`, требования —
в `specs/operations-filter/spec.md`.

Что есть сейчас и важно для решения:

- `DataFilter.getSQLFilter(fields)` строит `(from IN (все id)) OR (to IN (все id))`:
  кошельки и категории лежат в одном списке и не различаются.
- Колонки счетов передают три вызывающих места в `WalletDbLoader`:
  `reportFilterSql` (отчёты) и два вызова в загрузке ленты. Менять им нужно
  только результат `getSQLFilter`, не сигнатуру.
- Тап по строке кошелька (`AccountActivity`) и категории (`ReportActivity`)
  вызывает `state().setAccountIds(...)`: остальные параметры фильтра остаются.
  Это поведение остаётся как есть.
- Экран правки счёта — `AccountItemActivity` (его открывает `AccountPickerActivity`);
  `AddWalletActivity` и `AddCategoryActivity` только создают. Шапка
  `view_screen_header.xml` общая для 10 экранов и правого слота не имеет.
- Экран операции `TransactionActivity` знает обе стороны (`mAccFrom`, `mAccTo`),
  режим правки (`cIsEdit`) и поле комментария.
- Правок на сервере нет: фильтр целиком локальный, работает офлайн.

## Goals / Non-Goals

**Goals:**
- Два входа в готовый фильтр (из счёта и из операции) и крестик у каждого
  параметра в форме «Фильтр».
- Смысл «И» между группами категорий и кошельков без изменения формата
  хранения (`AppSettings.setFilterAccounts` по-прежнему хранит список id).

**Non-Goals:**
- Серверная часть и `wallet-api`; правка схемы базы; миграции.
- Чипы с крестиками в строке «Фильтр · …» над лентой — в этой задаче крестики
  только в форме «Фильтр».
- Изменение тапа по строкам в «Кошельки» и «Отчёты».
- Поиск «подобных» по сумме или дате.

## Decisions

**1. Группировка счетов внутри `DataFilter`, а не в хранении.**
`getSQLFilter` делит `accountList` по `AccountItem.isOperatingAccount()` на
кошельки и категории. Для каждой непустой группы строит
`(from IN (g) OR to IN (g))`, группы соединяет через `AND`. Хранение
(`accountIds`, `AppSettings`) не трогаем — деление выводится из справочника счетов,
как уже делает `FilterActivity.restoreSelection`. Альтернатива — хранить две
отдельные группы — потребовала бы миграции настроек и дублировала бы признак,
который уже есть у счёта. Id пропавшего счёта по-прежнему отбрасывается в
`rebuildDataFilter`.

**2. Сброс и установка фильтра — одним методом `PeriodFilterState`.**
Новый `presetFilter(ctx, accountIds, kind, searchText)` сначала сбрасывает всё
(`clearFilter`), затем ставит переданное; ревизия поднимается один раз на
каждый реально изменившийся параметр, как и в существующих сеттерах. Два входа
(счёт и операция) зовут именно его. Раздельные `clearFilter` + сеттеры в
каждом экране размножили бы порядок действий.

**3. Переход в «Операции» тем же способом, что и сейчас.**
`startActivity(new Intent(this, MainActivity.class).addFlags(FLAG_ACTIVITY_REORDER_TO_FRONT))`
— как в `AccountActivity` и `ReportActivity`. Лента перечитается в `onResume`
по сменившейся ревизии.

**4. Кнопка на экране счёта — в разметке `activity_account_item.xml`, не в общей шапке.**
Рядом с `screenTitle` добавляется `ImageButton` 40×40 dp, `bg_pill_secondary`,
`ic_filter`, `contentDescription` «Фильтр». Общую шапку не меняем: правого
слота нет у остальных девяти экранов, и он не должен появиться там случайно.
Показывается для существующего счёта (экран открывается только для существующего:
при `account == null` он закрывается), включая системные счета.

**5. «Найти подобные» берёт значения с экрана, а не из базы.**
Категория — сторона операции, не являющаяся кошельком; кошелёк — сторона-кошелёк;
у перевода обе стороны — кошельки. Комментарий — текущий текст поля, пустой не
передаётся. Тип операции — тот, что уже определяет экран (`deriveKind`); для
переоценки и прочих системных проводок, где типа нет, ставится «Все». Брать с
экрана, а не из базы, значит: если пользователь успел поменять счёт, не сохранив,
ищется то, что он видит. Кнопка — значок `ic_filter` в шапке рядом с «Удалить»,
`contentDescription` «Найти подобные»; видна только при `mIsEdit`.

**6. Крестики в форме «Фильтр» — наложенные `ImageButton` с `ic_clear`.**
Для полей ввода: поле оборачивается в `FrameLayout` (вес сохраняется на
обёртке), крестик лежит поверх у правого края, виден при непустом тексте
(тот же `TextWatcher`, что уже пересчитывает «Показать N»). Для строк «Счёт
затрат» и «Кошелёк»: когда выбор не пуст, шеврон заменяется крестиком;
нажатие очищает список, ставит «Все» и не открывает пикер. Для типа операции:
крестик после чипов, виден при типе не «Все», ставит «Все». Альтернатива —
`drawableEnd` на `EditText` с обработкой касания — отвергнута: хуже для
доступности и не подходит для строк и чипов.

## Risks / Trade-offs

- [Фильтр со смешанным выбором сузится] → это сам смысл задачи; изменение
  отмечено в `proposal.md` как BREAKING. Старый фильтр читается как раньше.
- [Операция с комиссией или переводом через промежуточный счёт] → в ленте
  ноги отображаются как отдельные проводки; фильтр работает по сторонам
  проводки, как и раньше, и отдельной логики для них не добавляется.
- [Группа категорий + перевод между кошельками] → перевод не проходит по
  группе категорий; это ожидаемо и закреплено сценарием «Перевод».
- [Крестик на поле, сидящем в узкой строке сумм] → крестик 24 dp внутри поля
  высотой 46 dp; текст получает правый отступ, чтобы не заходить под крестик.
- [Правка `getSQLFilter` задевает отчёты] → `reportFilterSql` использует тот же
  метод, поэтому отчёты «Доход» и «Расход» получают новую логику вместе с
  лентой; это согласовано с заметкой в `PeriodFilterState` о едином фильтре.
