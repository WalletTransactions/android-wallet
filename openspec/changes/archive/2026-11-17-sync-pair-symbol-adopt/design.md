## Context

Загрузка применяет строки в `SyncEngine.applyPage` → `applyRow` → `applyCurrencyPair` →
`upsertByUuid`. На телефоне уникальный индекс `uq_currency_pair_symbol` — один на все пары, а
на сервере их два: `uq_currency_pair_symbol_reference` (общие, `ledger_id IS NULL`) и
`uq_currency_pair_symbol_ledger` (пары кошелька, по `(ledger_id, symbol)`). Поэтому сервер
законно хранит рядом общую EURRUB и пару кошелька EURRUB с другим uuid, а телефон вместить обе
не может.

Наблюдение (qa на Pixel 7 Pro и база test, 2026-11-16):
- на телефоне 36 пар: 31 общая (синкнутые, uuid общих) и 5 пар кошелька (EURHRK, EURBAM,
  EURTZS, EURKES, EURALL — общих двойников у них нет);
- на сервере 36 живых пар кошелька, 31 из них — двойники общих по символу, пересозданные
  14 ноября в 14:24 со своими uuid; курсы кошелька (135) привязаны к ним;
- вставка этих 31 пар падает на `uq_currency_pair_symbol`, `upsertByUuid` возвращает `null`,
  `applyCurrencyPair` возвращает `true` (`SyncEngine.java:1558-1561`). Строка не применена и не
  отложена, курсор ушёл дальше (`ledgerSyncSeq = 56`), курсы остаются в отложенных (135).

Уже есть `LedgerConnection.adoptByKey`: заменяет uuid неотправленной локальной строки с тем
же ключом (`currency.iso_code`, `currency_pair.symbol`, `account.name`) на серверный и
сохраняет локальный `_id`, а значит и все ссылки по `_id`. Включается флагом
`SyncEngine.adoptLocalByKey` только на время подключения и ищет только `dirty <> 0`.

## Goals / Non-Goals

**Goals:**
- Пара кошелька с занятым символом не теряется: заменяет локальную общую или синкнутую пару,
  курсы и перерасчёты остаются на месте.
- Пара, которую разрешить нельзя, остаётся отложенной и видна пользователю.
- Телефоны, уже потерявшие пары, восстанавливаются сами (однократная перезагрузка).

**Non-Goals:**
- Серверный контракт, схема и данные сервера (дубль общей пары у кошелька — осознанное
  поведение сервера, этот change его не меняет).
- Те же конфликты у `currency.iso_code`/`currency.name`, `icon.name`, `account.name` —
  аналогичная проблема, но другая семантика; отдельные changes.
- Поведение при удалении пары кошелька, под которую подменили общую (см. «Риски»).
- Совместимость со старыми версиями клиента (принято: не поддерживаем).

## Decisions

**D1. Разрешение конфликта по символу — в `applyCurrencyPair`, а не в общем `upsertByUuid`.**
`upsertByUuid` общий для 12 таблиц, и «дубль пары» ему неизвестен. `applyCurrencyPair` знает
`ledger_id` пришедшей строки и может решить, чья пара главнее. Альтернатива «расширить
`adoptByKey` и включать его всегда» отвергнута: он ищет только `dirty <> 0`, а общие строки
синкнуты, и для `account` ослабление проверки опасно (имена счетов у разных пользователей).

**D2. Приоритет: пара кошелька над общей.**
Пара кошелька принадлежит пользователю и несёт его курсы; общая — справочник. Поэтому:
- пришла пара кошелька, символ занят общей, синкнутой или неотправленной → заменить uuid и поля
  у занявшей строки (`replaceUuid`, `dirty` остаётся 0, `from_seed = 0`, метка общей снимается);
- пришла общая, символ занят парой кошелька → не вставлять и вернуть `true`: штатный исход.
  Различить «занявшая строка — пара кошелька» можно по `is_shared = 0` (поле уже заполняет
  `isSharedRow`, см. «Общие строки справочника»).
- пришла пара, символ занят неотправленной — прежнее поведение `adoptByKey`, но без флага.

Порядок потоков при загрузке (`ledger` и `reference` вместе, таблицы по `TABLE_ORDER`) не важен:
результат один и тот же при любом порядке прихода общей и парной строк (идемпотентность).

**D3. Локальный `_id` сохраняется — курсы и перерасчёты переезжают сами.**
`currency_pair_rate.currency_pair_id` и `currency_conversion.currency_pair_id` ссылаются по
`_id`, uuid в них не хранится, так что `UPDATE currency_pair SET uuid = …` переносит всё. Курсы
пары, которые сервер пришлёт позже с `currency_pair_uuid` пары кошелька, найдут её по новому uuid.
Курсы, которые на телефоне уже лежали у общей пары (старые строки, по uuid общих курсов),
остаются: уникальность `(currency_pair_id, date)` на сервере и телефоне совпадает по ключу, дубль
на pull разрешает существующий `upsertByUuid` курса.

**D4. «Не разрешили — не обработана».**
Если замену выполнить не удалось (другой индекс, `SQLiteException`), `applyCurrencyPair`
возвращает `false` вместо `true`: строка попадает в `PullDeferredRows` и в журнал. Раньше она
исчезала молча; теперь видна («Часть данных ждёт…»). Остальные таблицы не трогаем (Non-Goals).

**D5. Однократная перезагрузка.**
Новый флаг `pairSymbolResyncDone` рядом с `deferredRowsResyncDone`. Условие в `SyncEngine`
(строка ~1014): `!isUuidFormatResyncDone || !isDeferredRowsResyncDone || !isPairSymbolResyncDone`
→ тот же путь «загрузка с нуля и вычистка» (`reloadPending`), та же строка журнала. Свежие
установки флаг получают без перезагрузки, там курсоры и так нулевые. Без этого телефон,
потерявший пару, не получил бы её: курсор уже за ней.

**D6. Серверных изменений нет.**
Сервер уже присылает оба варианта пары с их `ledger_id`; для клиента это единственный нужный
сигнал. Исправление данных на test (2026-11-16) — отдельное действие, не часть change.

## Risks / Trade-offs

- **Удаление пары кошелька после подмены**: если пользователь удалит пару кошелька, на телефоне
  строка получит время удаления, а общая пара с тем же символом не вернётся (сервер её не
  пришлёт повторно, позиция потока ушла вперёд). → Принято: удаление пар кошелька, подменивших
  общие, на телефоне пока не обслуживаем; при необходимости перезагрузка (D5-механизм) вернёт общую.
  Оформим отдельным change, если проявится.
- **Перезагрузка с нуля** вычищает синкнутые строки, которых сервер не прислал (`sweepUnseen`);
  неотправленные (`dirty <> 0`) остаются — потери пользовательских данных нет.
- **Несколько живых пар с одним символом на сервере** (в разных ledger) телефону не встречаются:
  один телефон — один кошелёк.
- **Офлайн**: правило локальное, сети не требует; без сети остаётся прежнее состояние.

## Migration Plan

Обычное обновление приложения; первый проход после обновления делает однократную перезагрузку.
Откат — установка предыдущей версии: данные в БД совместимы (меняются только значения `uuid`).
