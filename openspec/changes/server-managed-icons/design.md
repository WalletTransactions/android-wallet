# Design

## Context

- `SyncEngine.pushDirty` в каждом раунде собирает dirty-иконки
  (`collectDirtyIcons`): для каждой `ensureBlobUploaded` (HEAD + до 3
  попыток POST `/sync/blobs`), потом строка `icon` в push. Незалитая иконка
  и всё, что на неё ссылается, откладываются (`deferDependents`).
- Pull: `prefetchNewIconBlobs` качает байты новых иконок до транзакции,
  `applyIcon` вставляет новую / обновляет метаданные известной, конфликт
  уникального имени — пропуск с логом. `applyAccount`/`applyCurrency`
  резолвят `icon_uuid` → локальный `icon_id`.
- Таблица `icon` (v85; артефакты писались при v83 — номер шага сдвинут на
  v86, т.к. v84/v85 заняли правка точности синка и `currency-ui-tweaks`): `name UNIQUE`, `image` (WEBP 256×256), `uuid`,
  `dirty` (триггер `trg_icon_dirty` ставит 1 на любой UPDATE), `deleted_at`.
  Признака «откуда иконка» нет.
- Сервер: строки `account`/`currency` требуют существующего `icon_uuid`
  (`409 missing_reference`), общие иконки видны всем леджерам, свои — только
  своему. wallet-api продолжает принимать `icon` в push (для старых версий).
- В работе параллельный change `purge-synced-tombstones` (вычистка
  tombstone по `dirty = 0`) — пересекается по таблице `icon`.

## Goals / Non-Goals

**Goals:**
- Ни одного запроса загрузки иконок в проходе синка.
- Ни одна строка не теряется на сервере из-за своей иконки: у неё всегда
  есть серверная ссылка (заместитель).

**Non-Goals:**
- Отправка своих иконок на сервер «по требованию» или их перенос в общий набор.
- Удаление на сервере своих иконок леджеров, залитых прежними версиями.
- Замена картинки у иконки с сервера (сервер её тоже не поддерживает).

## Decisions

1. **Новая колонка `icon.origin INTEGER NOT NULL DEFAULT 0`** (0 — с
   сервера, 1 — своя), миграция v86: `UPDATE icon SET origin = 1 WHERE
   dirty = 1`, затем `dirty = 0` для всех иконок. Альтернатива — считать
   «своей» любую `dirty = 1`: ломается, потому что триггер `trg_icon_dirty`
   ставит `dirty = 1` на любой UPDATE, а `purge-synced-tombstones` чистит по
   `dirty = 0`. Отдельная колонка явная и не зависит от триггера.
   `IconEditDialog.saveNewIcon` пишет `origin = 1`; `applyIcon` при вставке —
   `origin = 0`. Pull строки с `uuid` своей иконки (она когда-то ушла на
   сервер, но после правки снова dirty) переводит её в `origin = 0` — сервер
   главный.
2. **Push без `icon`.** `collectDirtyIcons`, `ensureBlobUploaded`,
   `BLOB_UPLOAD_ATTEMPTS` и откладывание из-за незалитых иконок удаляются.
   `SyncApiClient.uploadBlob`/`blobExists` остаются неиспользуемыми → удалить
   вместе с тестами. `deferDependents` остаётся — теперь для строк без
   заместителя (п. 3).
3. **Заместитель вычисляется при сборке push** (`IconSubstitutes`, чистый
   класс с юнит-тестами): один раз за раунд строится индекс иконок `origin = 0`,
   живых — `sha256(image) → uuid`, `lower(name) → uuid`, и uuid `unknown`
   (общая, т.е. пришла в разделе `reference`; на телефоне общие и свои
   серверные не различаются, поэтому — просто иконка `origin = 0` с именем
   `unknown`). Хеш картинки иконки с сервера равен её `content_sha256`, так что
   отдельно хранить его не нужно; ~150 иконок по ~10 КиБ хешируются за
   миллисекунды. В `collect` для `currency`/`account`, если `icon_id`
   указывает на `origin = 1`, `icon_uuid` берётся из индекса; нет
   заместителя — uuid своей иконки кладётся в `deferred`, и существующий
   `deferDependents` откладывает строку с зависимыми, с новой формулировкой
   проблемы в журнал.
4. **Защита своей иконки на pull** в `applyAccount`/`applyCurrency`: если
   текущая локальная иконка строки `origin = 1` и пришедший `icon_uuid`
   совпадает с её заместителем по тому же индексу — `icon_id` в `cv` не
   кладём. Индекс строится один раз на страницу pull (после применения
   иконок страницы, т.к. `icon` первая в `TABLE_ORDER`).
5. **Конфликт имени на вставке иконки с сервера**: перед `insertOrThrow`
   ищем живую иконку с тем же именем; если она `origin = 1` — переименовываем
   её в «<имя> (своя)» / «(своя N)» в той же транзакции. Если `origin = 0` —
   прежнее поведение (пропуск, лог).
6. **UI:** `IconEditDialog` для `origin = 0` — режим просмотра: поля и
   кнопки скрыты, текст «Иконка с сервера — изменить или удалить её может
   администратор на сайте.». Модель `Icon` получает поле `fromServer`,
   `WalletDbLoader.LoadIcons` читает `origin`.

**Правки в других сервисах:** для этого change — нет. Общий набор
пополняет wallet-api (`POST /api/admin/icons`, свой change), wallet-web даёт
админу экран. wallet-telegram иконки не трогает.

**Без сети / при отказе сервера:** иконки теперь вообще не требуют сети на
отправке; своя иконка доступна сразу и офлайн. Pull без сети — как раньше
(новые иконки не скачаны, `prefetchNewIconBlobs` падает → проход «нет сети»).

## Risks / Trade-offs

- [Своя иконка уже была залита прежней версией, потом её переименовали — она
  станет «своей» после миграции (dirty = 1)] → на сервере остаётся прежняя
  копия; при следующем pull строки с тем же uuid иконка вернётся в
  `origin = 0` (п. 1). Не критично: картинка та же.
- [На другом устройстве/вебе счёт показывает заместитель, а не своё фото] →
  осознанный компромисс выбора «свои — только локально»; админ может добавить
  такую картинку в общий набор, и заместитель по SHA-256 станет точным.
- [Первый синк нового телефона: иконок с сервера ещё нет, а у пользователя
  есть свои] → push идёт до pull; строки со своими иконками отложатся одним
  проходом и уйдут следующим. Приемлемо; в журнале видно.
- [Пересечение с `purge-synced-tombstones`] → вычистка иконок по `dirty = 0`
  после миграции не затронет живые; своих tombstone не бывает (удаление
  своей — жёсткий DELETE, как сейчас).

## Migration Plan

Выкатка после wallet-api/wallet-web (иначе админ не сможет пополнить набор,
но телефон работает и без этого). Миграция v86 односторонняя по данным
(`dirty` иконок обнуляется); откат на старую версию приложения не поддерживается
Android (downgrade БД) — как и для прежних версий схемы.
