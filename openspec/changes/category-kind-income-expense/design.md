# Design

## Context

Мотивация — в `proposal.md`. Что есть сейчас в клиенте:

- Признаки счёта уже хранятся колонками на самой строке `account`: `system_kind`
  (v75) и `kind` (v76, кошелёк/категория), оба в `WalletContract.AccountEntry`,
  `WalletDbHelper.accountTableBody()`, шагах `onUpgrade`, SELECT'е push
  (`SyncEngine`, таблица `account`) и `applyAccount` pull. Вид категории
  повторяет этот путь. Версия БД сейчас 91 (`WalletDbHelper.DATABASE_VERSION`).
- Выбор статьи — `AccountPickerActivity` с типом `cSelectedTypeChargeAccounts`
  (категории). Он одинаков для расхода и дохода: в списке все не архивные
  категории (`buildRows`). Вызывают его `TransactionActivity`
  (`openAccountPicker`), `RecurringOperationActivity` (`onPickTop`),
  `AccountItemActivity` (перенос между категориями) и `DebtsActivity` (категория
  прощения долга).
- «Новая категория» — `AddCategoryActivity` (`WalletDbCRUD.InsertAccount`);
  правка — `AccountItemActivity` (`WalletDbCRUD.UpdateAccount`).
- Стартовый набор — `assets/seed.json`, поле `accounts`: 27 записей без вида
  (23 расходные, 4 доходные), 2 кошелька, 2 системные.
- Сервер (wallet-api, миграция `000041`) делает `category_kind` обязательным в
  push и сам разметил существующие категории всех леджеров: одним `next_seq` на
  леджер, строки доезжают через pull.
- Правка нужна только в клиенте; другие сервисы не меняются.

## Goals / Non-Goals

**Goals:**
- Приложение продолжает синхронизировать счета с обновлённым сервером.
- «Статья расхода» и «Статья дохода» предлагают только подходящие категории.
- Вид задаётся при создании категории и меняется в её карточке.

**Non-Goals:**
- Локальная разметка существующих категорий по операциям: разметка — на сервере.
- Фильтр по виду в отчётах, журнале, фильтрах и в категории ИИ-подсказки.
- Запрет менять вид у категории с операциями «не того» вида.
- Серверные проверки сочетания `kind`/`system_kind`/`category_kind`: их нет, и
  инвариант (кошелёк и системная категория — «Оба») держит клиент.

## Decisions

**D1. Колонка `account.category_kind`, версия БД 92.** `INT NOT NULL DEFAULT 2`,
значения `0` расход, `1` доход, `2` оба — те же, что на сервере. Шаг `v92` по
образцу v76: `ALTER TABLE … ADD COLUMN`, но только если колонки ещё нет
(апгрейд из очень старой базы получает её из `accountTableBody()`). Строки не
помечаются `dirty`, `uuid`/`seq` не трогаются: изменение схемы не должно
уйти на сервер как правка пользователя.

**D2. Разметка — с сервера, не локальная.** Альтернатива — на v92 размечать
категории по локальным операциям, как это сделал сервер. Отвергнута (так же, как
в design сервера): на телефоне могут быть неотправленные операции, и два
устройства разметят одну категорию по-разному. До первого pull после
обновления все категории — «Оба», то есть списки выглядят как раньше.

**D3. Push: колонка обязательна всегда.** SELECT в `collectDirtyByTable`
получает `category_kind`, строка `account` несёт `row.put("category_kind", …)`
наравне с `system_kind`/`kind`. Значение из базы, а не вычисленное: клиент
гарантирует `2` для кошельков и системных категорий тем, что колонка у них не
меняется (создание — умолчание, карточка выбора не показывает).

**D4. Pull: терпимо к отсутствию поля.** `applyAccount` читает
`row.optInt("category_kind", 2)` и значение вне `0..2` приводит к `2`.
Альтернатива — `getInt`, как для `system_kind`: она роняет строку в
«отложенные» при сервере без колонки. Сервер с колонкой уже есть, но клиент не
должен ломаться на старом контуре. Применённая с сервера строка не `dirty`
(`applySyncColumns` уже так работает).

**D5. Фильтр пикера — чистая функция.** Выбор показывает категорию, если
`category_kind` равен `2`, равен виду операции (`0` для «Статьи расхода», `1` для
«Статьи дохода»), либо категория — текущая выбранная в слоте, либо входит в
список приоритетных кандидатов ИИ/импорта (`cPriorityIds`, их предлагает
`AiActivity`/`StatementImportActivity` явно, и скрывать их было бы сюрпризом).
Логика выносится в отдельный класс `CategoryKindFilter` без зависимостей от
Android (юнит-тест на JUnit). `AccountPickerActivity.buildRows` применяет её
только при новом extra `cCategoryKind` (`0`/`1`); остальные вызовы (`DebtsActivity`,
перенос категорий, справочник) extra не передают и видят все категории, как
раньше. `TransactionActivity` и `RecurringOperationActivity` передают вид
операции (`Kind.expense` → `0`, `Kind.income` → `1`; перевод кошельков не
использует категорий).

**D6. Карточка и «Новая категория».** Три чипа в стиле существующих
(`paintChip`/`Chips`): «Расход», «Доход», «Оба», подпись «ВИД». Показываются
только у обычной категории (`!isOperatingAccount() && !isSystem()`).
«Сохранить» в карточке считает вид в `changed`. У новой категории по умолчанию
«Расход» — правило клиента (D2 сервера: сервер умолчание `2`, но клиентское
создание всегда осознанное). Запись — `WalletDbCRUD.InsertAccount`/
`UpdateAccount` получают `categoryKind` и помечают строку `dirty`.

**D7. Стартовый набор.** `seed.json` получает необязательное `category_kind` у
записей `accounts`; нет поля — `2`. `WalletFillData` читает его при заведении
категорий набора. Ключ — число, как у сервера, а не строка: набор потребляет
только код приложения.

**D8. JSON-обмен.** Экспорт пишет `category_kind` только у обычных категорий (у
кошельков и системных значение всегда `2`, ключа нет); импорт читает ключ
необязательным, значение вне `0..2` — `2`. Формат остаётся читаемым старым
импортом: лишний ключ там игнорируется. Альтернатива — строковые значения
(«expense»/«income»), как `"system": "revaluation"`: отвергнута, чтобы не
вводить второе представление одного и того же значения.

## Risks / Trade-offs

- [Неотправленная правка категории на момент обновления перезапишет серверную
  разметку: push уйдёт с `2`] → окно узкое (только строки `dirty` в момент
  апгрейда), вид меняется в карточке одним действием. Приложение не размечает
  локально, чтобы не плодить расхождений (D2).
- [Пока приложение без этой правки, сервер с `category_kind` отвечает `400` на
  push `account`] → релиз Android и prod-тег `v0.4.6` wallet-api идут вместе;
  на test серверная сторона уже выкачена.
- [Категория «Оба» после обновления везде, пока не пришёл pull] → поведение
  списков такое же, как до правки; разметка догоняет при первой синхронизации.
- [ИИ или импорт выписки предложили категорию «не того» вида] → кандидат
  остаётся в списке (D5); пользователь может принять или выбрать другую.
- [Отдельные пикеры, не получающие вид (перенос категорий, прощение долга)] →
  видят все категории; фильтровать там нечем и незачем.

## Migration Plan

1. `WalletDbHelper`: `DATABASE_VERSION = 92`, шаг `v92`, колонка в
   `accountTableBody()`, `WalletContract.AccountEntry.COLUMN_CATEGORY_KIND`.
2. `WalletDbLoader` / `AccountItem` читают и хранят вид; `CategoryKindFilter`.
3. `SyncEngine`: push и `applyAccount`.
4. Экраны: пикер, `TransactionActivity`, `RecurringOperationActivity`,
   `AddCategoryActivity`, `AccountItemActivity`; строки ru/en.
5. `seed.json`, `WalletFillData`, `WalletExportData`/`WalletImportData`.
6. Зеркало схемы и `docs/ARCHITECTURE.md`.
7. Проверка на Huawei (ru и en) против test-контура; затем релиз вместе с
   prod-тегом `v0.4.6` wallet-api. Откат: предыдущая сборка приложения не
   откатывает колонку (она безвредна), сервер откатывается по плану wallet-api.

## Проверено на устройстве (2026-11-15, Huawei P20 Pro, qa-сборка 1.0.160 против test `0.4.6-rc.1`)

- Миграция v92 на существующей базе: версия 92, колонка есть, у всех счетов `2`, ни одна
  строка не `dirty` (на сервер ничего не ушло).
- Первая синхронизация: pull доставил разметку сервера (1 расход, 1 доход, 26 «Оба»),
  значения на телефоне совпали с сервером, строки не помечены неотправленными.
- «Статья расхода» не показывает «Зарплата» (вид «Доход») и показывает «Списание долгов»
  (вид «Расход»); «Статья дохода» наоборот. Категории «Оба» видны в обоих.
- Новая категория «Ktest Bonus» с видом «Доход»: на сервере `category_kind` = 1 (`POST
  /sync/push` — 200), в «Статье дохода» есть, в «Статье расхода» нет. Смена вида на «Оба» в
  карточке: «Сохранить» неактивна до выбора, после сохранения и синка на сервере `2`.
  Удаление категории дошло до сервера (tombstone).
- Английская локаль: «TYPE» / «Expense» / «Income» / «Both», по умолчанию «Expense»; на узком
  экране переносов нет.
- Категории стартового набора, не размеченные сервером (без операций: «Подработка»,
  «Проценты», «Прочие доходы»), на уже установленном приложении остаются «Оба»; вид из
  `seed.json` применяется только на новых установках.

## Open Questions
