# Design

## Context

Мотивация и охват — в proposal.md. Что важно для подхода:

- Android офлайн-первый: операции и справочники живут в локальной SQLite и
  уходят на сервер синком (`SyncRunner.runOnce`: `AuthSession.ensureFresh` →
  `SyncEngine.pushDirty` → `SyncEngine.pullAll`). Связи в локальной базе
  хранятся по `_id`, протокол работает по `uuid`; перевод — `findIdByUuid`.
- wallet-ai при создании задания `parse_expense` берёт справочник счетов из
  wallet-report (`GET /api/reports/accounts`), то есть из **серверной** копии.
  Resolver возвращает `uuid` кошелька и категории из этой копии. Локальные
  изменения, ещё не отправленные push, для него не существуют.
- `runOnce` сейчас не защищён: `SyncWorker` (WorkManager, тот же процесс) и
  кнопка «Синхронизировать сейчас» (`IntegrationsActivity`) могут идти
  параллельно. Курсоры pull лежат в `AppSettings`, самолечение push
  (`redirty`, `resolveAccountConflicts`) не рассчитано на два прохода сразу.
- Веб уже реализует ту же функцию (`wallet-web` spec `ai-expense-entry`).
  Тексты и разбор результата берём оттуда, чтобы клиенты вели себя одинаково.

## Goals / Non-Goals

**Goals:**
- resolver работает по справочнику, совпадающему с телефоном, без ручного синка;
- ни одна операция не записывается на кошелёк или категорию, которых нет в
  локальной базе; пользователь видит, почему;
- без сети и при отказе wallet-ai приложение не ломается: ручной ввод доступен
  всегда.

**Non-Goals:**
- офлайн-разбор текста на устройстве (локальная модель, шаблоны);
- фоновые задания ИИ: задание интерактивное, живёт, пока открыт экран;
- изменения серверов и их контрактов.

## Decisions

### 1. Предварительный синк — полный `runOnce`, а не только push

```
[Разобрать]
   |
   v
SyncRunner.runOnceShared(ctx, timeout ~10 s)        (фоновый поток)
   |
   +-- OK / PARTIAL ------------> POST /api/ai/jobs
   +-- NETWORK_ERROR / ERROR ---> POST /api/ai/jobs + плашка
   |   / таймаут                  «Справочник мог не дойти до сервера: <причина>»
   +-- NO_SESSION / NEEDS_RELINK > без задания, «Войдите в аккаунт»
   |
   v
GET /api/ai/jobs/{id}?wait=25 (повтор, пока queued/running)
   |
   v
черновик -> сверка uuid с локальной базой (решение 3) -> карточка
```

- Push нужен, чтобы сервер узнал о кошельках и категориях, созданных или
  удалённых на телефоне. Pull нужен, чтобы телефон знал кошельки, созданные в
  вебе или боте: иначе resolver вернёт `uuid`, которого локально нет.
- Отдельный «лёгкий» синк (только справочники) не делаем: `pullAll` тянет оба
  потока по общему курсору, и делить их — правка протокола.
- **Таймаут.** Экран ждёт синк не дольше ~10 с. После этого задание создаётся,
  а синк продолжает работать (его не прерываем: push порциями, оборвать
  посреди — хуже). Медленным бывает в основном первый полный pull
  (`ledgerSeq == 0`).
- **Синк не удался.** Задание всё равно создаётся (решение пользователя:
  вариант А), под полем — плашка с `Outcome.errorMessage`. Если черновик потом
  сошлётся на неизвестный кошелёк, сработает решение 3.

Альтернатива — только предупреждать о dirty-строках и не синковать. Отклонена:
пользователю пришлось бы самому идти в «Интеграции».

### 2. Синк один на процесс

`SyncRunner` получает общий замок и «идущий проход»:

- `runOnce` (воркер, кнопка) и новый `runOnceShared` (экран «ИИ») проходят
  через один `synchronized`/`ReentrantLock` на классе;
- если проход уже идёт, вызывающий не запускает второй, а ждёт его `Outcome`
  (общий `Future`). Экран «ИИ» ждёт с таймаутом из решения 1, воркер и
  кнопка — без таймаута, как сейчас;
- результат чужого прохода годится: для resolver важно, что push и pull
  закончились, а не кто их запустил.

- время последнего прохода с исходом `OK`/`PARTIAL` `SyncRunner` пишет в
  `AppSettings` (сейчас оно нигде не хранится), его читает блок ошибки из
  решения 3.

Так закрывается и существующая гонка кнопки с воркером. WorkManager работает в
том же процессе (отдельного `:process` в манифесте нет), поэтому замка в памяти
достаточно.

Альтернатива — `enqueueUniqueWork` для всего синка и ожидание `WorkInfo`.
Отклонена: кнопке и экрану «ИИ» нужен подробный `Outcome` с `SyncLog`, а
`WorkInfo` вернёт только код.

### 3. «Кошелёк пропал» — сверка черновика с локальной базой

После получения черновика каждый `uuid` из `resolution` (выбранный кошелёк,
категория, `candidates`, `force`) переводится в локальную строку `account`:

| Состояние локально | Что видит пользователь |
|---|---|
| нет строки с этим `uuid` | «Кошелька «<имя>» нет на телефоне» |
| `deleted_at` не null | «Кошелёк «<имя>» удалён на телефоне» |
| `is_archived = 1` | «Кошелёк «<имя>» в архиве» |

Для категории — те же тексты со словом «Категория». `<имя>` берётся из ответа
resolver: локального имени может не быть.

Поведение:
- блок ошибки под карточкой; поле очищено, «Записать» неактивна, карточка и
  остальные поля сохраняются;
- в блоке детали: результат предварительного синка этого разбора (статус и
  `errorMessage`, если не OK), время последнего успешного синка, хвост `uuid`
  (последние 8 символов — для отладки, без текста пользователя);
- «Синхронизировать и повторить»: снова `runOnceShared` и повторная сверка
  **того же** черновика, без нового задания и без LLM;
- «Выбрать другой»: локальный список кошельков (категорий);
- кандидаты `ask`, которых нет локально, молча убираются из списка; если не
  осталось ни одного, показывается тот же блок ошибки.

Сверка выполняется дважды: при показе карточки и ещё раз непосредственно перед
`InsertOperation` (кошелёк могли удалить, пока карточка открыта).

### 4. Запись — локально, как обычная операция

«Записать» вызывает `WalletDbCRUD.InsertOperation` с локальными `_id` кошелька
и категории. Строка получает `dirty=1` и уходит обычным синком. После записи
экран ставит фоновый `runOnceShared` без ожидания, чтобы трата быстро дошла до
сервера (и до веба/бота). Нужно обновить `Singleton`/`OperationList`, как это
делает `TransactionActivity`.

Отличие от веба: прямого `POST /sync/push` нет, поэтому не нужны `batch_id`,
повтор с тем же `uuid` и обработка `device_required`. Запись работает и без
сети, если черновик уже получен.

### 5. Доступность пункта «ИИ»

- Нет сессии (`TokenStore` пуст) → пункт неактивен: «Войдите, чтобы пользоваться ИИ».
- `GET /api/ai/status` при открытии «Ещё» (кэш на время жизни экрана):
  `enabled: false` или нет `parse_expense` в `features` → «ИИ сейчас выключен».
  Сеть недоступна → «Нет связи с сервером».
- Экран «ИИ» всегда показывает «Заполнить вручную» (открывает обычный
  `TransactionActivity` с текстом в комментарии), поэтому отказ wallet-ai
  не мешает записать трату.

### 6. Клиент wallet-ai

`sync/AiApiClient` на общем `HttpClients` (как `SyncApiClient`): `status`,
`createJob`, `getJob(wait)`, `cancelJob`. Перед вызовами — `AuthSession.ensureFresh`.
Ожидание — цикл `getJob?wait=25` на фоновом потоке. Тайм-аут чтения OkHttp
должен быть больше 25 с: нужен отдельный `newBuilder().readTimeout(...)`.
Уход с экрана или «Отменить» → `DELETE /api/ai/jobs/{id}`, поздний ответ
игнорируется. Поля входа:
- `now` — локальные дата и время телефона;
- `default_wallet_uuid` — `uuid` кошелька последней записи с экрана «ИИ»
  (`AppSettings`), только если он жив локально;
- `idempotency_key` — `android:<uuid>`, новый на каждое «Разобрать».

Коды ошибок и тексты (`429`, `503`, `404`, `not_expense`, `rejected`, `failed`)
берём из веба.

### 7. Ввод: «Поделиться» и голос (п. 1a)

- `AiActivity` объявляет `intent-filter` `ACTION_SEND` / `text/plain`. Текст
  подставляется в поле, задание **не** запускается само: пересланный текст
  (Viber, SMS) часто длиннее 500 символов и содержит лишнее, пользователь
  правит и жмёт «Разобрать». Длиннее 500 — счётчик подсвечен, кнопка неактивна.
- Голос — кнопка-микрофон, системный `RecognizerIntent.ACTION_RECOGNIZE_SPEECH`
  (`ru-RU`, `EXTRA_PREFER_OFFLINE`). Разрешение `RECORD_AUDIO` не нужно.
  Распознанный текст подставляется в поле, автозапуска нет. Если распознавания
  на устройстве нет (`resolveActivity == null`), кнопка скрыта.
- Если экран «ИИ» открыт через «Поделиться», а входа в аккаунт нет, экран
  показывает причину и «Заполнить вручную» с текстом в комментарии.

### Правки в других сервисах

Нет. google-auth, wallet-gateway, wallet-ai, wallet-api, wallet-report
используются по текущим контрактам.

## Risks / Trade-offs

- [Предварительный синк замедляет «Разобрать» на секунды] → таймаут ~10 с, в
  обычном случае push+pull — одна-две страницы; прогресс «Синхронизирую…» →
  «Разбираю…», чтобы ожидание было объяснено.
- [Синк по таймауту продолжает работать в фоне] → это безопасно благодаря замку:
  следующий вызов дождётся его, а не пойдёт параллельно.
- [Замок задерживает кнопку «Синхронизировать сейчас», пока идёт проход воркера]
  → кнопка получает результат того же прохода; это честнее, чем сейчас.
- [Распознавание речи может уйти в облако Google, если офлайн-пакета нет]
  → `EXTRA_PREFER_OFFLINE`; текст и так уходит на свой сервер wallet-ai,
  отдельного согласия не делаем, но упоминаем в README.
- [wallet-report отстаёт от wallet-api сразу после push] → обе службы читают
  одну Postgres. Если отставание всё-таки появится, сработает сверка из
  решения 3 с «Синхронизировать и повторить».
- [Resolver выбрал кошелёк, который на телефоне в архиве, хотя на сервере
  активен] → блок ошибки «в архиве», пользователь выбирает сам; автоматически
  не разархивируем.
