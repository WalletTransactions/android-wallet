# Design

## Context

Эквивалент на устройстве считают SQL-запросы поверх `v_currency_conversion_rate`
(`v_operation_eq`, `LoadBalancesPerWallet`, карточка периода, `AccountOperatingItem`):
шаблон «`max(date)` не позже даты, join обратно по дате». `v_operation_eq`
делает cross join операций со всеми валютами. `currency_conversion` в схеме
есть (синкается, `SyncEngine.applyCurrencyConversion`), но всегда пуста и UI
у неё нет. Сервер (wallet-api, одноимённый change, PR #45) считает курс
функцией `rate_on`: прямой → маршрут → кросс через USD.

## Goals / Non-Goals

**Goals:** тот же результат, что на сервере; потребители курса (SQL) не
меняются; маршруты заводятся и удаляются на телефоне, едут в синк.
**Non-Goals:** свой поиск пути по графу пар, альтернативные маршруты,
совместимость со старыми клиентами синка, настройка хаба вместо USD.

## Decisions

### 1. Составные курсы — локальная таблица-кэш, а не вьюха с кроссом
Вьюха «всё в одном» (исходный замысел) на сервере не вычислилась (замер в
design wallet-api), а на устройстве `v_operation_eq` и так умножает операции на
валюты. Поэтому составные курсы считает Java (`DerivedRates.rebuild`) и пишет
в таблицу `currency_rate_derived(from_currency_id, to_currency_id, date, rate)`
(PK по трём колонкам, не синкается); `v_currency_conversion_rate` добавляет её
строки к прямым и тождественным. Потребители не меняются: они видят обычные
строки `(from, to, date, rate)`, фильтр по `from/to` идёт по индексу таблицы.

### 2. Что и для каких пар считается
Целевые валюты — только те, что предлагаются как эквивалент
(`currency.show_in_equivalent = 1`, живые): так число строк растёт как n × k, а
не n². Для пары `(S, E)`, `S ≠ E`, без живого прямого курса (в любую сторону,
на любую дату): явный структурно валидный маршрут (шаги — последний курс не
позже даты независимо, даты = объединение дат шагов, обратное направление
`1/произведение`); нет маршрута — кросс через USD по двум прямым шагам; валидный
маршрут без курса блокирует USD. Обе стороны (`S→E` и `E→S`) пишутся.
Курсы применяются по тем же правилам видимости, что у остальных (живые строки,
`deleted_at IS NULL`).

### 3. Когда пересчитывать
Любое изменение исходных данных курса (курс пары, пара, валюта, шаги
маршрутов) помечает кэш устаревшим (`derived_rates_stale`, триггеры SQLite); перед
чтением кэш перестраивается одной транзакцией, если помечен (`DerivedRates.
ensureFresh` при выдаче базы). Перестройка полная — данных мало (десятки валют,
тысячи курсов). Правки через CRUD, пакет pull синка и импорт работают через те
же таблицы, поэтому отдельных вызовов не требуют.

### 4. Таблица `currency_conversion` и миграция
Версия БД 93: таблица пуста у всех, поэтому пересоздаётся (SQLite не меняет
ограничения): `PRIMARY KEY (from, to, num)` сохраняется, добавляются
`CHECK (num BETWEEN 1 AND 3)` и `from <> to`. `dirty`/`deleted_at`/`uuid` —
как у остальных синк-таблиц. Вьюха `v_currency_conversion` перестаёт подмешивать
`currency_conversion` в направления пар (строки таблицы теперь шаги, а не
подмена пары) — как на сервере.

### 5. Операции с маршрутом
`WalletDbCRUD`: `listRoutes` (живые валидные), `createRoute(путь из валют)`
(подбор пары: базовая валюта «слева», иначе обратная; своя пара раньше общей;
один набор шагов в транзакции, dirty = 1), `deleteRoute(from, to)` (мягко,
все шаги). Удаление пары (`WalletDbCRUD.deleteCurrencyPair…`) каскадно гасит
маршруты с её шагами.

### 6. Экран
`CurrencyRouteListActivity` — по спеке `list-screen-layout` (шапка, список,
нижняя пунктирная кнопка «+ Маршрут»); вход — чип/кнопка «Маршруты» на экране
«Курсы валют». Форма — диалог с выбором 3–4 валют (пикер валют уже есть).
Тексты — `values` и `values-ru`, CI-проверка hardcoded text.

### 7. Другие сервисы
Правка серверов не нужна: контракт синка — wallet-api (PR #45, `currency_conversion`
LedgerOnly, построчные проверки), выкат wallet-api → android-wallet.

## Risks / Trade-offs

- [Кэш устаревает, если забыть пометку] → триггеры на всех четырёх источниках,
  юнит-тест на каждую (курс, пара, валюта, шаг).
- [Полная перестройка на каждое изменение] → данные малы; замер на тестовой
  базе, при необходимости — перестройка только затронутых пар.
- [Расхождение с сервером на деталях] → одни и те же сценарии (спека
  `currency-routes`) прогнаны юнит-тестами и там и тут.

## Migration Plan

1. Версия БД 93: пересоздать `currency_conversion`, создать `currency_rate_derived`,
   триггеры устаревания, пересоздать вьюхи, первый `rebuild`.
2. Выкат: wallet-api (есть) → android-wallet. Откат — переустановка с экспортом данных.
