# Design

## Решения

**D1. Формат.** Расширение чисто аддитивное, без смены версии формата:

```json
{
  "counterparties": [
    {"name": "Вася", "comment": "", "icon": "unknown", "archived": false}
  ],
  "accounts": [
    {"name": "Вася · USD", "comment": "...", "icon": "...",
     "currency": {"iso": "USD"},
     "debt": {"counterparty": "Вася", "comment": "", "due_date": "2026-12-31"}},
    {"name": "Квартира", "currency": {"iso": "RUB"},
     "asset": {"type": "real_estate", "include_in_net_worth": true, "comment": ""}},
    {"name": "Переоценка", "system": "revaluation"}
  ]
}
```

`asset.type`: `real_estate` | `vehicle` | `other` (строки, а не числа 1/2/3 —
файл читает человек). `debt.counterparty` — имя; контрагент связывается по
имени по тому же правилу, что уникальность (`AccountNames.keySql`: без
регистра, пробелов по краям, ё/е). `due_date` — `yyyy-MM-dd`, необязателен.

**D2. Порядок применения:** контрагенты → счета → пары → курсы → операции.
Блок `debt` ссылается на контрагента, поэтому тот должен быть заведён раньше;
если контрагента нет в `counterparties`, но имя в `debt.counterparty` есть —
импорт заводит его на лету (конвертер и ручные файлы не обязаны дублировать).

**D3. Идемпотентность по имени.** Контрагент и счёт с занятым именем не
дублируются, а обновляются (как уже делает импорт счетов). Блок `debt`/`asset`
у существующего живого кошелька оживляет/обновляет строку `account_debt`/
`account_asset` (мягкое удаление и повторная пометка — те же правила, что на
экранах).

**D4. Взаимоисключение.** Кошелёк не может быть одновременно долговым и
активом (так на экранах). Элемент с обоими блоками пропускается с причиной;
пометка уже-долгового кошелька активом (и наоборот) — тоже пропуск.
Блоки у категории (без `currency`) — пропуск с причиной.

**D5. Переоценка.** Отдельного раздела нет: переоценка — обычная операция
через системную категорию (`system_kind = REVALUATION`). Экспорт помечает эту
категорию `"system": "revaluation"`; импорт ставит `system_kind` и не заводит
вторую, если «Переоценка» уже есть (как `GetOrCreateSystemCategory`). Остальные
значения `system` игнорируются: `Transfer`/`Transfer commission`, как и
раньше, распознаются по имени.

**D6. Что не экспортируется.** `counterparty_contact` (локальная привязка к
контакту), uuid и служебные поля синка. Иконка контрагента — по имени иконки,
как у счетов; нет живой иконки — `unknown`.

**D7. Устойчивость.** Незнакомые ключи игнорируются; неверный `asset.type` или
формат `due_date` — пропуск элемента с причиной «accounts#N — …», остальной
файл применяется (общая транзакция и правила «целиком или никак» не меняются).

## Риски

- Переименование контрагента в файле и на телефоне: имя — единственная связь,
  поэтому конфликт разрешается по имени, а не создаёт дубль.
- Импорт в чужой леджер заводит контрагентов, общих для участников, — это
  ожидаемо и совпадает с поведением экрана «Долги».
