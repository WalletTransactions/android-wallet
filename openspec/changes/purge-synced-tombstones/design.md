# Design

## Context

- Синкающиеся таблицы локально: `icon`, `currency`, `currency_pair`,
  `currency_pair_rate`, `currency_conversion`, `account`, `account_operating`,
  `operation`, `operation_link`; у каждой `uuid`, `dirty`, `deleted_at`.
  Удаление в UI — мягкое (`deleted_at`), чтение фильтрует `deleted_at IS NULL`.
- `PRAGMA foreign_keys = ON` (`WalletDbHelper`); на счета ссылаются ещё и
  локальные таблицы без синка (повторяющиеся операции).
- `SyncEngine.pushDirty` снимает `dirty` (`clearDirty`) только после ответа
  сервера на порцию. `pullAll` сохраняет курсоры после применения страницы.
- Сброс от сервера (`reset`) сейчас просто тянет поток с нуля: строки, которых
  нет на сервере, остаются на телефоне. Пока сервер хранит все tombstone, это
  не проблема; после чистки на сервере (wallet-api change) — проблема.

## Goals / Non-Goals

**Goals:**
- Локальная база не копит отправленные удаления.
- Загрузка с нуля приводит локальную базу к состоянию сервера, не теряя
  неотправленное.

**Non-Goals:**
- Чистка локальных таблиц без синка (повторяющиеся операции, черновики ИИ).
- Экран или кнопка ручной чистки.

## Decisions

**1. Чистка — отдельный шаг после `pullAll` в `SyncRunner`, только если
`pullAll` завершился без исключения.** К этому моменту все удаления, которые
надо отправить, отправлены (`dirty = 0`), а пришедшие — применены. Чистка после
неуспешного push-а безопасна сама по себе (условие `dirty = 0`), но шаг
держится после успешной загрузки, чтобы не удалить строку, ссылку на которую
вот-вот принесёт незагруженная страница. Без сети проход до чистки не доходит —
ничего не удаляется.

**2. Удаление построчно, ошибка внешнего ключа — пропуск строки.** Порядок
таблиц от листьев к корням (`operation_link` … `icon`), для каждой —
`SELECT uuid … WHERE deleted_at IS NOT NULL AND dirty = 0`, затем `DELETE` по
uuid; `SQLiteConstraintException` → строка остаётся. В SQLite ошибка FK
откатывает только этот оператор, не транзакцию. Альтернатива `NOT EXISTS` по
всем ссылкам требует помнить и локальные таблицы без синка — забытая ссылка
сломает чистку. Объём на телефоне небольшой, построчно приемлемо.
Перед удалением `icon` — то же правило: иконка, на которую ссылаются, остаётся.
Удаление не должно поднимать `dirty` у других строк — проверить триггеры
`trg_*_dirty` (они на `UPDATE`/`INSERT`, не на `DELETE`).

**3. Tombstone для отсутствующей строки пропускается в `apply*`.** Иначе
загрузка с нуля создаёт строки только затем, чтобы чистка их удалила, и пишет в
журнал «Удалено» для того, чего пользователь никогда не видел.

**4. Загрузка с нуля — mark-and-sweep с отметками в базе.** Новая таблица
`sync_reload_seen(tbl TEXT, uuid TEXT, PRIMARY KEY(tbl, uuid))` и флаг
`AppSettings.fullReloadPending`. Флаг ставится, когда `pullAll` начинает с нуля
(курсор 0 при непустых синкающихся таблицах, `reset`, смена кошелька,
починка uuid), и сохраняется вместе с обнулением курсоров. Каждая применённая
страница при поднятом флаге пишет uuid своих строк (живых и удалённых) в
`sync_reload_seen` в той же транзакции. Когда оба потока догнаны — удаляются
строки с `dirty = 0`, которых нет в `sync_reload_seen` (тем же построчным
удалением из решения 2), таблица очищается, флаг снимается. Прерванная
загрузка продолжается с сохранённого курсора, отметки уже в базе.
При `reset` любого потока обнуляются оба курсора: поток справочников мал, а
локально не различить, какой поток принёс строку.
Альтернатива «стереть всё синкнутое и загрузить заново» ломает внешние ключи:
неотправленная операция ссылается на синкнутый счёт.

**5. `ledger_id` в `pull` — из `AppSettings.getSyncLedgerId`, если не null.**
`reset_reason` читается в `PullStream` только для лога (`"purged"` → «Сервер
очистил старые удаления — загружаю данные заново»), поведение одинаковое для
любой причины.

**Правки в других сервисах:** wallet-api, change `purge-synced-tombstones`
(подтверждения, `ledger_id`, `reset_reason`, чистка). Клиент совместим со
старым сервером: лишний параметр игнорируется, `reset_reason` отсутствует.

## Risks / Trade-offs

- [Строка, вычищенная локально, нужна для разбора конфликта имени счёта
  (`resolveAccountConflicts`)] → он работает с живыми строками; удалённые
  счета в нём не участвуют — проверить при реализации.
- [Вычистка при загрузке с нуля удалит строку, которую сервер не отдал из-за
  своей ошибки] → удаляются только `dirty = 0`, то есть строки, уже бывшие на
  сервере; сервер — источник правды. Неотправленное не трогается.
- [Миграция БД (версия 83) на устройствах] → только новая таблица, данные не
  меняются; проверить апгрейд с 82.
- [Чистка на сервере включена раньше, чем телефоны обновились] → порядок
  выката описан в design.md wallet-api: чистка на сервере включается после
  релиза этого change.
