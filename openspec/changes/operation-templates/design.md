# Design

## Context

Мотивация и состав изменений — в `proposal.md`, требования — в дельта-спеках. Здесь —
как это ложится на текущий код `android-wallet`.

Что есть сейчас:

- Правило повторяющейся операции — одна строка таблицы `recurring_operation`
  (`acc_fr_id`, `acc_to_id`, `amount`, `comment`, расписание, `is_active`, `last_date`),
  класс `RecurringOperation` (расписание считает `occurrencesBetween`, без Android),
  слой `RecurringOperationsDb`. Таблица локальная: триггеров `dirty` и `uuid` нет, в синк
  не входит.
- Генератор `RecurringOperationsDb.generateDue` на каждый повтор вставляет **одну**
  операцию через `WalletDbCRUD.InsertOperation`. Связок и комиссии он не знает.
- Комиссию за перевод пишет `TransactionActivity`: отдельная проводка и
  `WalletDbCRUD.LinkOperations(mainId, linkId, OperationItem.LinkType.COMMISSION)`
  (`operation_link.type = 1`).
- На `recurring_operation` по счёту ссылаются: `SyncEngine.cascadeGuard` (чистка
  tombstone не должна молча унести правило), `LedgerConnection` (очистка при смене
  леджера), `ReminderWorker.hasEnteredToday` (операция «как у правила» не считается
  введённой человеком), `WalletDbCRUD` (перенацеливание правил на актив),
  `ResetDataActivity`, `WalletFillData`.
- Версия БД — 93 (`WalletDbHelper.DATABASE_VERSION`), миграции — цепочка `oldVersion < N`.

Правок в других сервисах (`google-auth`, `wallet-api`, `wallet-ai`, `wallet-gateway`)
**не требуется**: таблицы шаблонов локальные и не входят в `kApplyOrder` /
`TABLE_ORDER`. На сервер уходят только обычные операции и их связки, как и сегодня.

Сеть не нужна ни для запуска, ни для генератора. Офлайн-поведение то же, что у
любой новой операции: запись локальная, на сервер — с ближайшим синком.

## Goals / Non-Goals

**Goals:**
- Одна модель «шаблон = заголовок + шаги + необязательное расписание» вместо двух
  сущностей (правило и будущий шаблон).
- Одна функция раскладки суммы по шагам, которой пользуются и ручной запуск, и
  генератор, — чтобы результат не расходился.
- Модель сразу рассчитана на много шагов и на будущую синхронизацию (uuid), при этом
  UI первой версии — основная проводка плюс необязательная комиссия.
- Миграция существующих правил без потери данных и без повторного создания операций.

**Non-Goals:**
- Синхронизация шаблонов и поведение на втором телефоне (см. ниже).
- Форма с произвольным числом шагов, перестановка шагов.
- Разновалютные шаги и ввод суммы получателя.
- Общая связка «шаблон → созданные им операции».
- Комиссия у расхода и дохода в форме (в модели возможна, в форме — только у перевода).

## Decisions

### 1. Новые таблицы вместо переделки `recurring_operation`

Заводятся `operation_template` и `operation_template_step`; `recurring_operation`
после переноса удаляется (миграция v94).

```
operation_template                       operation_template_step
  _id, uuid UNIQUE                         _id, uuid UNIQUE
  name NOT NULL                            template_id -> operation_template ON DELETE CASCADE
  comment NOT NULL DEFAULT ''              num INTEGER NOT NULL        -- порядок, с 1
  total_amount DECIMAL(15,2) NULL          acc_fr_id -> account ON DELETE CASCADE
  -- расписание: либо всё, либо ничего     acc_to_id -> account ON DELETE CASCADE
  frequency INTEGER NULL                   amount_mode INTEGER NOT NULL -- 0 фикс, 1 %, 2 остаток
  interval, week_days                      amount_value DECIMAL NULL    -- число для фикс и %
  start_date TEXT NULL                     comment NOT NULL DEFAULT ''
  end_date TEXT NULL                       commission_of_num INTEGER NULL -- номер основного шага
  is_active, last_date                     UNIQUE(template_id, num)
```

Расписание «есть» тогда и только тогда, когда `frequency IS NOT NULL`; тогда
`start_date NOT NULL`. Это проверяется `CHECK`.

Рассмотрено и отклонено:
- *Добавить в `recurring_operation` nullable-расписание и колонки шага.* Таблица
  сделана под одну проводку; шаги пришлось бы хранить в соседней таблице, а имя
  «повторяющаяся» к ручному шаблону не подходит. Переименование всё равно трогает все
  места из списка выше.
- *Хранить шаги JSON-колонкой.* Теряем внешние ключи на счета: каскад при физическом
  удалении счёта и защиту `cascadeGuard` пришлось бы писать вручную.

`uuid` у шаблона и шага заводится сразу, хотя синка нет: на нём держится любой из
будущих вариантов синхронизации, а добавить его позже — отдельная миграция всех
телефонов. Триггеров `dirty` не создаём, `change_stream` не трогаем.

### 2. Раскладка суммы — чистый класс без Android

`TemplateLayout.expand(steps, total, precision)` → список сумм по шагам или ошибка.
Арифметика — `BigDecimal`, не `double`: `double` в `RecurringOperation.amount` годится
для хранения, но не для «остаток = общая − Σ». Правила:

1. Фикс — как есть. Процент — `total × p / 100`, округление `HALF_UP` до `precision`
   (точность валюты кошелька шагов, ту же берёт окно операции).
2. Остаток — `total − Σ(остальные)`; единственный; обязан быть строго больше нуля,
   иначе ошибка «Фиксированные суммы и проценты больше общей суммы».
3. Результат — список «шаг → сумма» в порядке `num`.

Класс покрывается юнит-тестами (сценарии 1550 → 1500 + 50, 3 % → 46,50, три доли
по 33,333 %, остаток = 0, остаток < 0) и вызывается из экрана запуска, генератора и
`ReminderWorker`.

*Процент — от общей суммы, а не от «чистой» суммы основной проводки.* 1 % от 1550 —
это 15,50, а не 15,00. Так проще и однозначно (нет циклической зависимости: комиссия
от суммы, которая включает комиссию). Для реальных комиссий банкомата, которые чаще
фиксированные или «процент, но не меньше N», этого достаточно. «Процент от суммы
основного шага» отложен (см. «Открытые вопросы»).

### 3. Запуск — свой экран, а не предзаполнение `TransactionActivity`

Запуск открывает экран «Запуск шаблона» (общая сумма, дата и время, список проводок
с правкой). Для первой версии (основная проводка + комиссия у перевода) можно было бы
открыть окно операции уже заполненным и переиспользовать его комиссию, но окно умеет
ровно одну проводку и комиссию только у перевода: набор из N шагов в нём не
выразить, и пришлось бы потом делать второй путь. Свой экран делает шаблон
общим механизмом, а `TransactionActivity` остаётся для ручного ввода.

Запись — один метод `OperationTemplatesDb.apply(db, template, amounts, at)`: в
транзакции вставляет проводки (`InsertOperation`), затем связывает комиссии
(`LinkOperations(..., COMMISSION)`), оборачивается в `DebtAutoArchive`, как
генератор. Тот же метод вызывает генератор на каждый повтор — отсюда одинаковое
поведение вручную и по расписанию.

### 4. Комиссия — роль шага, а не отдельная сущность

Шаг с `commission_of_num = N` после вставки связывается с проводкой шага N связкой
`type = 1`. Допустимо, если шаг N — не комиссия и списывает с кошелька (как главная
проводка в окне операции). Категория комиссии по умолчанию — системная «Комиссия за
перевод» (`AccountItem.SYSTEM_COMMISSION_NAME`, заводится лениво при создании
шаблона, чтобы запуск и генератор не создавали счета).

Форма перевода с комиссией порождает два шага: основной (`остаток`) и комиссию
(`фикс` или `%`, «со счёта отправителя» — кошелёк-источник → категория; «со счёта
получателя» — кошелёк-получатель → категория), `commission_of_num = 1`. Правка
формы пересобирает шаги из полей; шаги, которые форма не умеет (не она их создавала),
в версии 1 не появляются — других источников шагов нет.

### 5. Расписание отдельно от шагов

`RecurringOperation` делится: расписание (`frequency`, `interval`, `weekDays`,
`startDate`, `endDate`, `isActive`, `lastDate`, `occurrencesBetween`,
`nextOccurrence`, `describeSchedule`) переезжает в `TemplateSchedule` без изменения
логики — существующие unit-тесты расписания переносятся с минимальной правкой. Класс
`OperationTemplate` держит заголовок, шаги и необязательное расписание.

Генератор: для каждого включённого шаблона с расписанием считает повторы после
`lastDate`, на каждый вызывает `OperationTemplatesDb.apply` с `total_amount`
шаблона. Шаблон пропускается (дата не сдвигается), если хотя бы один счёт шага
мягко удалён или раскладка ошибочна (например, пользователь позже поменял комиссию
на большую, чем общая сумма). Одна транзакция на запуск генератора, как сейчас.

### 6. Миграция v94

Одна транзакция внутри `onUpgrade`:

1. Создать обе таблицы с `CHECK` и индексами по `uuid`.
2. Для каждой строки `recurring_operation` (порядок по `_id`): шаблон с новым uuid,
   `total_amount = amount`, расписание и `last_date` как были; шаг `num = 1`,
   режим «остаток», `comment` = старый комментарий, `commission_of_num = NULL`.
   Название: комментарий; иначе имя «другой стороны» — счёта без строки в
   `account_operating` (категория), а у перевода — источника; иначе «Повторяющаяся
   операция». Имя берётся в Java при переносе, не SQL-выражением.
3. `DROP TABLE recurring_operation`.

`last_date` и `is_active` переносятся дословно, поэтому генератор после обновления не
досоздаёт и не повторяет ничего. Отката нет: ни старый клиент, ни данные старой
схемы не поддерживаются (обратная совместимость не требуется). Свежая установка
(`onCreate`) сразу создаёт новые таблицы.

### 7. Переключение ссылок на счета

| Место | Было | Стало |
| --- | --- | --- |
| `SyncEngine.cascadeGuard("account")` | правило ссылается на счёт | шаг ссылается на счёт |
| `LedgerConnection` | `acc_fr_id/acc_to_id` из `recurring_operation` | то же из `operation_template_step` |
| `WalletDbCRUD` (перенацеливание на актив) | UPDATE правил | UPDATE шагов с теми же условиями |
| `ResetDataActivity`, `WalletFillData` | очистка таблицы правил | очистка шагов, затем шаблонов |
| `ReminderWorker.hasEnteredToday` | SQL по `recurring_operation` | Java: раскладка по шаблонам с расписанием |

Физическое удаление счёта каскадно удаляет шаги; шаблон без шагов остаётся пустым
и должен убираться тут же (триггер `AFTER DELETE` на шагах или явная чистка в
`SyncEngine.purgeTombstones`; выбор — при реализации, поведение «удаляется и шаблон
целиком» зафиксировано в спеке).

`ReminderWorker`: операция «похожа на периодическую» теперь, если её счета и сумма
совпадают (с точностью до 0,005) с одним из шагов раскладки **шаблона с
расписанием** при его `total_amount`. Ручные шаблоны не считаются: операция,
запущенная человеком, — «внесённая». Сравнение переезжает из SQL в Java (операций за
день единицы, шаблонов десятки).

### 8. Экраны

- `OperationTemplateListActivity` — список по `list-screen-layout`: поиск «Поиск по
  названию», нижняя `ListAddButton` «+ Добавить шаблон», строка со вторым
  рядом (расписание, «Вручную»), переключатель включения у шаблонов с расписанием.
  Тап — запуск, долгое нажатие — меню «Изменить» / «Удалить».
- `OperationTemplateActivity` — форма: поля шаблона, комиссия (переиспользуются
  разметка и логика блока комиссии `TransactionActivity`, вынесенные в общий
  компонент, а не скопированные), блок расписания из `RecurringOperationActivity`.
- `OperationTemplateRunActivity` — запуск.
- `RecurringOperationListActivity` и `RecurringOperationActivity` удаляются, их
  строки в `strings_recurring.xml` переименовываются (ru/en), `MoreActivity` ведёт
  в список шаблонов. Диалог «Пропущенные повторы» переезжает в форму шаблона.
- Все новые тексты — в `strings` для ru и en (проверка hardcoded-text в CI).

## Вне объёма: что будет на втором телефоне

Таблицы шаблонов не синхронизируются, поэтому второй телефон шаблонов **не видит**, а
операции, созданные по ним на первом, получает обычным синком. Если шаблон завести
на обоих телефонах вручную с расписанием, каждый создаст свои операции, и в ленте
будут дубли: у операции новый случайный uuid, и сервер не отличит «ту же операцию
второй раз». Защиты не вводим, ровно как и у правил сегодня.

Варианты на будущее (решение не принято, `uuid` в модели заложен под любой):

| Вариант | Поведение | Риск |
| --- | --- | --- |
| Синкать только «рецепт» (заголовок и шаги), расписание локально | Шаблон виден везде и запускается вручную; расписание включают на одном телефоне | При включении расписания на двух телефонах — дубли |
| Расписание закреплено за устройством-исполнителем | Все видят расписание, исполняет одно | Нужны поле устройства и правило смены |
| Детерминированный uuid операции = хеш(шаблон, дата повтора, шаг) | Оба телефона создают одинаковые операции, сервер сворачивает | Меняет генератор; усложняет правку и удаление повтора |

Рекомендация: первый вариант, затем при необходимости третий. Для первого
потребуется новая таблица в `wallet-api`, новые строки в `kApplyOrder` и
`TABLE_ORDER`, изменение протокола синка и совместимость версий клиентов —
отдельный change.

Остальное вне объёма:
- **Общая связка «шаблон → созданные операции»** (новый `operation_link.type`): примера,
  которому она нужна, нет. Добавляется позже новым значением перечисления —
  изменение протокола, но небольшое.
- **Разновалютные шаги:** в шаблоне запрещены (одна валюта на шаблон). Позже можно
  разрешить с вводом суммы получателя при запуске; в генераторе это невозможно
  (зависит от курса на дату), поэтому для шаблонов с расписанием запрет останется.

## Risks / Trade-offs

- **Миграция теряет смысл полей** → тест на копии БД версии 93 с правилами всех
  частот, выключенным и закончившимся; сверка `lastDate`, `isActive`, расписания и
  отсутствия новых операций после первого запуска генератора.
- **Процент считается от общей суммы** (не от «чистой») → фиксируется в спеке и
  подсказке к полю («% от общей суммы»); пересмотр — через «Открытые вопросы».
- **Шаблон с расписанием может стать ошибочным позже** (комиссия увеличена, счета
  архивированы) → генератор пропускает шаблон, не сдвигая `lastDate`; пользователь
  видит это в строке списка. Отдельное уведомление в этом change не делаем.
- **Много мест с `recurring_operation`** (см. таблицу) → каждое закрывается задачей
  и проверкой `grep recurring_operation` по `app/src/main` на пустой остаток.
- **Исчезновение пункта «Повторяющиеся операции»** → справочная и пользовательская
  справка обновляются вместе с экраном (`user-guide`).
- **Длинные требования** (предупреждения `openspec validate`) → соответствуют
  существующим спекам проекта (например, «Поля правила» была длиннее); разбивать
  по требованиям не будем.

## Migration Plan

1. Реализовать таблицы, миграцию v94 и перенос данных с тестом на дампе БД v93.
2. Перевести генератор и ссылки на счета на шаги (одним PR с миграцией, иначе
   сборка не замкнётся).
3. Добавить экраны и пункт «Ещё», затем убрать старые экраны правил.
4. Обновить `docs/ARCHITECTURE.md`, `schema/table/README.md`, пользовательскую
   справку.
5. Проверка на телефоне: Huawei P20 Pro (основной тестовый), RU и EN, обновление с
   установленной предыдущей версии с правилами.

Откат релиза: не предусмотрен — миграция одноразовая; восстановление — из экспорта
базы (`data-export`).

## Open Questions

- Нужен ли режим «% от суммы основного шага» (а не от общей), когда появится форма
  с несколькими шагами? Не меняет модель — добавляется новым значением
  `amount_mode`.
- Как выбирать между триггером и явной чисткой для шаблонов, оставшихся без шагов
  после физического удаления счёта (детали реализации, поведение определено в спеке).
