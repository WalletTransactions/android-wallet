# Представления

Синхронизировано с `WalletDbHelper.CreateViews`, `DATABASE_VERSION = 72`. Приёмы,
общие для нескольких вьюх (раскрытие пары в оба направления, шаблон «курс на дату»),
разобраны в [`docs/ARCHITECTURE.md`](../../docs/ARCHITECTURE.md), раздел «Схема базы» →
«Представления».

**v72** (org/docs/TODO_mobile_sync.md, Фаза 3): каждая вьюха ниже получила фильтр
`deleted_at IS NULL` на участвующих таблицах — мягко удалённая строка (см.
`../table/README.md`, колонка `deleted_at`) не должна выглядеть живой. Исключение
одно, тоже зеркальное серверной вьюхе `schema/server/view/v_operation.sql`:
`v_operation` не фильтрует сами `account`/счета-стороны проводки по их
`deleted_at` — операция на мягко удалённый счёт обязана остаться видимой в
истории, иначе лента молча теряла бы строки. Раньше в этой схеме соответствующих
вьюх не было в принципе (никакого софт-делита не существовало) — правки описаны
по месту ниже.

## `v_account_operating`

```
account LEFT JOIN account_operating ON account_operating._id = account._id
```

Все счета, включая категории. У категории `currency_id` — `NULL`, и это не
техническая случайность `LEFT JOIN`, а отражение факта: у категории (статьи
расхода/дохода) своей валюты нет и быть не может. Валюта операции по категории
определяется **второй стороной проводки** — операционным счётом (кошельком),
см. `v_operation.currency_id` (`COALESCE(aof.currency_id, aot.currency_id)`).
Потребители этой вьюхи (например `LoadBalancesPerWallet`) сами добавляют
`JOIN currency`, что естественным образом отсекает строки без валюты, то есть
категории.

| Поле | Источник |
| --- | --- |
| `_id`, `name`, `comment`, `icon_id` | `account` |
| `currency_id` | `account_operating`, `NULL` для категорий |

## `v_account_expanse`

```
account LEFT JOIN account_operating ... WHERE account_operating._id IS NULL
```

Обратный фильтр к `v_account_operating` — счета без строки в `account_operating`:
те, что выступают **второй стороной проводки**, откуда списываются или на которые
зачисляются средства (категории расходов и доходов), а не сами кошельки. Определена
в схеме, но ни один текущий SQL-запрос в Java-коде её не использует: фильтрация
категорий на экранах идёт через `AccountList` на стороне Java, а не через эту вьюху.

## `v_currency_conversion`

Строит маршрут для поиска коэффициента/курса пересчёта одной валюты в другую:
разворачивает каждую `currency_pair` в **два** направления (`base → quote` и
`quote → base`, с флагом `is_reverse`), затем левым джойном подмешивает
переопределение из `currency_conversion` (которая в текущей версии всегда пуста —
см. `../table/README.md`), поэтому на практике всегда возвращает пары как есть.

| Поле | Смысл |
| --- | --- |
| `from_currency_id/name/iso`, `to_currency_id/name/iso` | Валюты направления |
| `currency_pair_id` | Пара, из которой получено направление |
| `num` | Всегда `1` в текущих данных (переопределения из `currency_conversion` нет) |
| `is_reverse` | `1`, если направление — это перевёрнутая пара (`quote → base`) |

Смысл приёма: запросы выше по стеку спрашивают курс `from → to`, не заботясь о том,
в какую сторону задана пара в `currency_pair` — обратное направление здесь уже готово.

## `v_currency_conversion_rate`

Курс на дату по каждому направлению из `v_currency_conversion`, с уже применённым
`1.0/rate` для обратного направления, плюс через `UNION` — тождественный курс `1`
для конвертации валюты в саму себя (дата `'2000-01-01'`, гарантированно самая ранняя).

| Поле | Смысл |
| --- | --- |
| `from_currency_id/name/iso`, `to_currency_id/name/iso` | Валюты направления |
| `date` | Дата курса |
| `rate` | Курс `to` за 1 `from`, уже с учётом разворота пары |

`is_reverse`/`num`, участвующие в вычислении `rate`, наружу этой вьюхой не
выводятся — только использованный ими результат.

## `v_operation`

Операция с раскрытыми именами счетов, валютой и признаками «операционный ли счёт»
с каждой стороны.

| Поле | Смысл |
| --- | --- |
| `_id`, `date`, `acc_fr_id`, `acc_to_id`, `amount`, `comment` | Из `operation` |
| `acc_fr_name`, `acc_to_name` | Имена счетов |
| `currency_id` | Валюта операционной стороны (`account_operating.currency_id` того счёта, у которого он есть) |
| `acc_from_is_operating`, `acc_to_is_operating` | `1`/`0` — есть ли у стороны строка в `account_operating` |

## `v_operation_eq`

`v_operation` + курс на дату операции + сумма в эквиваленте, для каждой валюты
эквивалента (`cross join currency`). Реализует шаблон «курс на дату» точечно для
операций: `max(date)` по датам курса не позже даты операции, затем джойн обратно за
самим курсом.

| Поле | Смысл |
| --- | --- |
| Все поля `v_operation` | |
| `to_currency_id` | Валюта эквивалента, для которой считается эта строка |
| `max_date_rate` | Дата найденного курса (последняя не позже даты операции) |
| `rate` | Курс `currency_id → to_currency_id` на `max_date_rate` |
| `amount_eq` | `round(rate * amount, 2)`; `NULL`, если курса не нашлось |

Основа для отчётных запросов `../select/GetIncomeForPeriod.sql` и
`../select/GetExpanseForPeriod.sql` (фильтр по направлению `acc_from_is_operating` /
`acc_to_is_operating` отличает доход от расхода).

## Черновики, не входящие в текущую схему

Не создаются `WalletDbHelper.CreateViews`; ни один Java-запрос к ним не обращается.

### `v_account_operating_balance.sql`

Более ранняя попытка того же расчёта, что сейчас живёт в
`WalletDbLoader.LoadBalancesPerWallet` (единственная актуальная реализация, см.
`../select/GetBalanceToDate.sql`).

### `v_currency_conversion_max_date_rate.sql`

Черновик пересчёта курса через несколько валютных пар подряд (геометрическое
произведение, `EXP(SUM(LOG(rate)))`). Зависит от `r.is_reverse`/`r.num`, которые
текущая `v_currency_conversion_rate` не выводит — то есть не заработает на текущей
схеме даже если её создать. Актуальный (однопарный) расчёт курса на дату — в
ARCHITECTURE.md, раздел «Курс на дату».
