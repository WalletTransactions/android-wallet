# План работ: перевод между счетами — комиссия и вторая валюта

## Что уже сделано

Одна операция на экране — одна или несколько проводок в базе, связанных через
таблицу `operation_link` (`main_id` / `link_id`, схема v71, миграция
инкрементальная — существующие операции не трогает).

`main_id` — всегда проводка списания с кошелька-источника; к ней цепляются и
вторая нога, и комиссия, поэтому по любой проводке находится вся операция.

Пишет это `TransactionActivity.saveTransfer()`:

- **одинаковые валюты** — одна проводка кошелёк→кошелёк;
- **разные валюты** — две ноги через системную категорию `Transfer`, связанные
  между собой: у `operation` одна колонка `amount`, а сумм тут две, в разных
  валютах. Вторая берётся из поля, куда её подставили по курсу на дату операции
  (`WalletDbLoader.LoadRateOnDate`), но подтвердить её должен пользователь;
- **комиссия**, если включена, — отдельная проводка с кошелька выбранной стороны
  («откуда» или «куда») на категорию комиссии, тоже связанная с главной.
  Категория по умолчанию — `Transfer commission` (заводится на месте, если её нет
  в старой базе), но её можно сменить на любую категорию трат. Сумма набирается
  той же экранной клавиатурой, что и остальные суммы.

Всё пишется в одной транзакции: либо все проводки операции, либо ни одной.

## Что осталось

### 1. Удаление операции целиком — сделано

Лента схлопывает связанные проводки (`WalletDbLoader.AttachLinkedOperations` →
`OperationItem.LinkedLeg` / `LinkedCommission`, рисует `TransactionArrayAdapter`
строкой `transaction_item_transfer.xml`), правка их разбирает и собирает обратно
(`TransactionActivity.loadLinkedParts` / `saveEdit` / `updateCommission`).

Опознавание ноги — по `system_kind` её счёта-источника (`AccountItem.SystemKind.TRANSFER`),
а не по совпадению id со «случайно» уже загруженным `mAccTo`/`op.AccTo`
(`loadLinkedParts`, `WalletDbLoader.AttachLinksTo`) — раньше это работало только
потому, что перевод и так всегда идёт через категорию `Transfer`, но сам код
этого не проверял.

`btnDeleteClick` — для одиночной операции обычное подтверждение; для операции с
ногой и/или комиссией — `showDeleteGroupDialog()`: список всех частей с
чекбоксами (по умолчанию отмечены все, что равносильно прежнему безусловному
удалению группы), можно снять отметку и оставить, например, сам перевод, удалив
только комиссию. `deleteOperation(int[])` мягко удаляет отмеченные id — строки
`operation_link` не трогает, они переживают soft-delete, как и раньше.

Замечание про `ON DELETE CASCADE` остаётся верным на будущее: это ограничение
сработало бы только при настоящем `DELETE`, которого код операций сегодня не
делает (кроме «Удалить все операции» на табе «Ещё» — та сносит таблицу целиком
и это отдельный, осознанно не тронутый путь, см. `schema/client/table/README.md`).

### 2. Старые данные — вариант Б сделан (импорт вперёд), вариант А (задним числом) не начат

Переводы, приехавшие импортом из MoneyLover, связей не имеют:
`MoneyLover_csv_Import/db.py` таблицу `operation_link` создаёт, но не заполняет —
пару (`f=766 t=767`) он знает и кладёт только в промежуточную
`csv_import_operation_raw`. В текущей базе (данные ДО этой правки) через `Transfer`
проходит 221 операция, через `Outgoing transfer` — 327, `Incoming transfer` — 283 —
их это не связывает, см. вариант А ниже.

**Вариант Б — новый JSON-импорт (сделано).** Плоский CSV органически не может
выразить «эта проводка — часть той группы»: одна строка = одна проводка. JSON
выражает связь структурно, без промежуточного ключа для матчинга:

- `Android/app/src/main/java/.../Data/WalletImportData.java`:
  `FillOperationDataFromJson` — один элемент массива = одна пользовательская
  операция, с опциональными `leg`/`commission`; пишет теми же примитивами
  (`InsertOperation`+`LinkOperations`), что и `TransactionActivity.saveTransfer()`,
  то есть путь импорта и путь ручного ввода перевода делят один и тот же код
  связывания. Формат описан в её же комментарии и в `cErrorMessage`
  (`ImportActivity`).
- `Activities/ImportActivity.java` + `activity_import.xml` — четвёртая секция
  «Операции JSON», кнопка `ImportOperationJsonClick`.
- `Activities/Fragments/FilePickerFragment.java` — тип файла в пикере расширен
  до `*/*` (был `text/*`, не всегда матчит `.json` у документ-провайдера).
- `tools/moneylover/main.py` — опция `export_json_operations` (по умолчанию
  включена): рядом с `trans.csv` пишет `trans.json` тем же циклом сопоставления
  переводов (строки ~296-341), что уже вычисляет обе ноги — теперь без
  промежуточного `ids`-ключа, сразу одной структурой с `leg`. Комиссия
  (эвристика по note `"Transfer fee "`/`"Комиссия за перевод "`) в JSON не
  связана ни с чем — как и раньше, скрипт не находит, к какому именно переводу
  она относится; уходит обычной проводкой.

**Вариант А — досвязать уже импортированные данные задним числом — не делали.**
Зацепки для этого остаются те же: одинаковая дата, одинаковый склеенный
комментарий (`Received from … / Send to …`), соседние `_id`. Это эвристика по
уже лежащим в базе операциям (в отличие от варианта Б, где пара известна точно,
на исходных MoneyLover-данных) — нужен отдельный разовый проход с отчётом о
том, что именно связалось, а не молчаливый запуск при старте. Пригодится, только
если понадобится связать данные, уже завезённые СТАРЫМ CSV-путём.

### 3. Отчёты — сделано

Пока валютный перевод состоит из двух ног через категорию, он попадал и в доход,
и в расход: `GenerateExpanseReportByAccount` брал `acc_from_is_operating = 1 AND
acc_to_is_operating = 0` (нога кошелёк→`Transfer`), `GenerateIncomeReportByAccount` —
обратное условие (нога `Transfer`→кошелёк). Каждый такой перевод раздувал обе
цифры карточки за период; итог (разница остатков) при этом был верный.

Обе ноги (по `operation_link.type = 0`, а не по счёту — на «Transfer» можно
завести и разовую ручную операцию, пикер её не прячет) теперь исключены из
своих гросс-сумм; их net (credit минус debit — обычно это и есть весь спред
перевода) добавляется одной строкой на счёте `Transfer` в тот список, куда net
попадает по знаку: положительный — в доход, отрицательный — в расход. См.
`WalletDbLoader.GetTransferNetEq`/`GenerateIncomeReportByAccount`/
`GenerateExpanseReportByAccount` и зеркально `f_income_for_period.sql`/
`f_expanse_for_period.sql` на сервере.
